## 1. md2case v2

### 1.1 mapping.yaml

```yaml
sections:            # 段落标题 → 字段与解析类型（标题可用别名，全角半角标题均可）
  问题: {field: question, type: text}
  对话: {field: dialog, type: dialog}
  对话记录: {field: dialog, type: transcript}
  关键条件: {field: conditions, type: conditions}
  注入: {field: injections, type: injections, prefix: J}
  前提: {field: preconditions, type: preconditions, prefix: P}
  必要事实: {field: facts, type: facts, kind: required, prefix: F}
  期望事实: {field: facts, type: facts, kind: expected, prefix: E}
  禁止事实: {field: facts, type: facts, kind: forbidden, prefix: X}
  路径: {field: path, type: path}
  证据: {field: evidence, type: evidence, prefix: R}
  变体: {field: variants, type: variants, prefix: V}
rewrites: [口语, 极简, 语序, 诱导]     # 【改写】合法值
tags: {业务: […], 场景: […], 难点: […], 来源: […]}
```

### 1.2 解析

- frontmatter：PyYAML safe_load；字段校验按 CASE-STRUCTURE §2.2。
- 段落切分：`## ` 二级标题；标题查 mapping（含别名/全半角归一），未命中报错；首标题前不得有正文。
- 属性：行尾 `【名称：值】` 序列，首个冒号切分，值按 `、` 分隔；正文中出现 `【` 报错。属性合法性表按 §2.4（名称 × 段落类型）。
- 四种输入形态归一为 `turns[]: {role, content}` + `assistant_refs[]`：
  - 列表：每项一轮 user；
  - `### 小节`：小节内文本为该轮 user，`助手：` 起为该轮参考回复；
  - jsonl 代码块：`{"role","content"}` 每行一条；
  - 对话记录段：`用户：/助手：`（含 User:/Assistant:）起始行切消息，连续助手合并。
- 变体：单行文本型（【轮次：N】【改写：x】，无轮次=最后一轮）；【整段】型取随后的嵌套列表为全部轮次。编译时按规则替换生成该变体的 turns（轮数、对象须与种子一致，check 校验）。

### 1.3 knowledge 加载与编译行

- `knowledge/*.yaml` 全量加载为 `points: {id → {file, key, tags, options{name → {value, rev}}}}`；id 冲突报错。
- `@point/option` → `{id:Jn, point, option, rev, file, key, value}`；同 point 多 option 报错；point/option 不存在报错。
- 证据 `@point` → `{id:Rn, doc: {skill: <file 首段或 point 所属 skill>, file}, section: null, quote: key}`；skill 名从 file 推导（平铺 `trade-x.md` → `trade-x`；bundle `trade-x/SKILL.md` → `trade-x`）。
- 证据内联：`skill:file / 章节 ｜ 原文：quote`；缺 `:file` 报错（无默认值，CASE-STRUCTURE §2.11）。
- 标签合并：用例 tags（场景/难点/来源）+ 注入点继承（业务/*），每条带 `from: case | point:<id>`。
- 输出行 = CASE-STRUCTURE §6 结构 + `evalset_version` + 执行侧定位字段 `case_id`/`variant_index`（契约只增不改）；uid = `<id>#<变体序>`，种子 #0。

### 1.4 check（无 --docs 与有 --docs 两档）

报错清单按 CASE-STRUCTURE §8 逐条实现，每条带 `文件:行号`；提示清单同理。`--docs <roots,...>` 追加三条：注入点 key 在 file 中找不到（报错）；内联证据原文找不到（报错）；key 出现在 frontmatter name/description（报错）；key 命中次数 ≠1（提示）。

### 1.5 build、diff 与 rev 联动

- 默认只收 admitted（`--include reviewed,admitted` 可放宽）；任何报错即不产出。
- `--prev <旧 dist>` 时生成 diff.md 五类：新增（uid 只在新）/ 退役（只在旧且源 status=retired）/ 因降级移出（只在旧且源 status=structured，附 status_note 末条）/ 内容修订（两版同 uid 编译行不等）/ rev 变化（同 uid injections.rev 不同）。
- rev 联动：`.knowledge-state.json` 记 `{case_id: {point/option: rev}}`。build 时对比当前用例引用的 rev 与状态文件：有变化 → 将该 md 的 frontmatter `status` 重写为 `structured`、`status_note` 追加 `<point>/<option> rev a→b，需复核`，该用例本轮不入 dist（除非 --include 放宽且再次校验通过）；随后状态文件更新为本次值。新引用直接登记不触发降级。

### 1.6 命令面

`check <paths> [--docs ROOTS]`、`convert <file>`、`build <paths> -o OUT --version V [--prev PREV] [--include STATUS…]`、`render <in> -o DIR [--force]`。全部只依赖 PyYAML。

## 2. runner 扩展

### 2.1 Profile（校验规则）

```yaml
id / model / dsh{bin, profile, profile_files?, timeout_ms} / skills_mode: default-roots|isolated
skills_roots: [path…]            # isolated 必填且非空；default-roots 时忽略
skills_inventory: path           # isolated 必填
budget: {max_tokens?, max_hours?}
skill_tool / routing / web{home, port}   # 沿昨日
```

校验：`skills_mode=isolated` 时要求 skills_roots、skills_inventory 存在且文件可读；`profile_files` 未给时默认取 profile 目录三件套（cordis.patch.yml、cordis.yml、package.json，存在即计入）。

### 2.2 环境快照（store 计算，写入 run.json `snapshot`）

| 键 | 算法 |
|---|---|
| evalset | 文件名 + sha256 |
| runner_profile | Profile 文件 sha256 |
| eline_profile | method=resolved：执行 `dsh … --print-profile`（若 CLI 支持，实现时探测一次）取输出 sha；否则 method=files：对 profile_files 清单（默认三件套）按内容拼接 sha。写 `{method, sha256, files?}` |
| skills_mode | Profile 值 |
| skills_base | isolated：各根下全部文件的 `(relpath, content)` 排序后哈希；default-roots：默认根可见 skill 的名称+内容清单哈希（经 skills-inventory 的同款计算，盘点不存在时对 `~/.dsh/skills` 兜底并标记 `approx: true`） |
| agent | bin 解析出的 CLI 名称与 `--version` 输出 |
| models_observed | run 结束汇总自逐轮 observations.model |

### 2.3 planner（步骤 0–3）

- 0 环境检查：inventory 的 `agent_version` 与实测不符、或其 `roots[].manifest_sha256` 与实测不符 → 计划提示 `inventory_stale`（写入 run.json）。
- 1 筛选：`--dims/--only/--topic`；**全量 run**（三者皆未指定）默认并入 anchors.txt（`--anchors on|off` 覆盖），锚点 trials = max(N,2)，run.json `anchors` 单列；锚点 uid 不在 dist → 提示。
- 2 能力适配（跳过原因写入 run.json）：prefill 不支持；forced 无 topic/无 routing；forced 目标被路径 `禁止`（跳 forced 留 natural）；`skills_mode != isolated` 时的 ec（`isolation-not-verified`）；注入 file 不在基底；**注入预演** found=0（`injection-key-missed`）。预演 = 对基底文件只读统计 key 出现次数，found>1 进提示清单。
- 3 展开：`uid × mode × trial` → 计划项 `{seq, uid, mode, trial, turns, injections, forcedSkill?, anchor?}`。
- 成本估算：总轮数 × 最近同 Profile run 的每轮平均 token/耗时（读 out/ 下最新 run.json 的 actuals），÷ 并发数；超 budget 提醒不阻断；无历史则只报会话数与轮数。

### 2.4 materialize（isolated 时，EpisodeRunner 准备阶段）

1. 复制各 skills_roots → `.work/<ep>/skills/<i>/`；同名 skill 按 inventory 的生效来源仅保留一份（inventory 记 `skills[].root`）。
2. 应用 injections：`key → value` 精确替换（全部匹配；value 空即删除），统计 `found`。
3. `found=0` → Episode status=error（`injection-key-missed`），不发送；`found>1` 如实记录。
4. overlay 追加（与会话落盘重定向并列）：

```yaml
- id: skill-filesystem
  name: '@deepseek-ai/dsh-skill-filesystem'
  config: {includeDefaultRoots: false, customSkillDirs: ["<ep>/skills/0", "<ep>/skills/1"]}
```

5. `skills_sha256` = 副本 `(relpath, content)` 排序哈希；无注入会话与 snapshot.skills_base 不等 → run.json 告警。

### 2.5 vendor/probes 修复与扩展（W2）

- **collector 兼容**：tool/result 事件字段在该版本位于 `data.message.source.callId / data.message.toolCallId`，解析器增加嵌套回退读取；text 从 `data.message.content[].text` 聚合。修复判据：对昨日 forced episode 回归，trade-finance/trade-finance-policy 由"失败"转"成功"。
- **model 观测**：新增解析 `request/header` 事件的 `data.header.config.{provider, model, reasoningEffort}` → `observations.model`（缺失记 null）。
- **ask_user 观测**：工具探针对 `ask_user` 工具调用计数，结果含超时/跳过语义时记 `auto: true`（字段名 `ask_user: {count, auto}`）。
- **错误原因码**：dsh-cli 适配器对 stderr/退出输出做模式匹配（`429|rate limit` → `rate-limited`；`session id` 相关 → `session-invalid`；其余 `unknown`），写入轮与 Episode 的 `error.code`。

### 2.6 EpisodeRecord（schema 3）与 store

在昨日 schema 2 基础上：+`case`（编译行原样）、+`skills_sha256`、+`injections_applied[]`（含 found）、+`observations.{ask_user, model}`、+`error.code`、+`anchor` 标记；快照移入 run.json（行内只留 evalset_version）。run.json 新增：snapshot、跳过清单（原因分组）、预演提示、anchors、`estimate` 与 `actuals`（总 token/耗时）、`model_drift`、`skills_mismatch`、`inventory_stale` 告警。续跑一致性检查五键：evalset、runner_profile、eline_profile、skills_mode、skills_base。

### 2.7 CLI

`run --cases <md 目录或文件>… --profile --out   # 直接 md 启动：现场编译 adhoc-<时间戳> 一次性评测集（试跑用，不参与对比/续跑）
`run --evalset --profile --out [--modes] [--trials] [--concurrency] [--dims] [--only] [--topic] [--anchors on|off] [--dry-run] [--resume] [--max-error-rate] [--keep-workspace]`；`inspect <ep-dir>`（沿昨日，输出增加 model 字段样例）。

## 3. scoring v2

### 3.1 判定管线（单 episode）

1. 前提：`preconditions[].text` 逐条交 `precond_judge(text, 对应轮 output) → 成立/不成立`（judge 缺省用规则：输出含要点关键词比例实现可插拔）；任一不成立 → `invalid: true`。
2. 事实 F/E/X：有 keywords → 规则判（关键词出现且前 4 字内无否定词 → pass，否则交 judge）；无 keywords 或规则不决 → `fact_judge(text, output) → 对/部分/错/未提及`。F 需全"对"且无 X 采信才 pass；E 仅统计；X 由 `forbidden_judge(text, output) → 采信/未采信`（复述不算采信）。
3. 路径：按 CASE-STRUCTURE §2.10 表实现（截至 N 轮已加载 / 第 N 轮发生 / 全程任一轮）；forced 记 n/a。
4. 汇总：episode.pass、episode.invalid、分组 `direct | after_ask`（observations.ask_user.count>0）。
5. 判定快照：输出头部 `{judge_model, judge_prompt_sha, rule_version}`，scoring 自算。

judge 接口（沿昨日函数注入风格）：`fact_judge(fact, answer) -> '对'|'部分'|'错'|'未提及'`、`forbidden_judge(fact, answer) -> bool`、`refusal_judge(answer) -> bool`、`precond_judge(text, answer) -> bool`。

### 3.2 聚合与视图

- 聚合：dim × topic × mode 的通过率与前提成立率（分母=运行 ok 会话）、Wilson 95% 区间；ec headline=forced；natural 三分归因（目标 skill 取 path 必须，缺省 routing 映射）。
- `compare <runA> <runB> [--diff diff.md]`：打印快照差异键（含判定快照；method 不同单独提示；skills_mode 不同拒绝比较）→ 按 uid 配对通过率差 + 区间 → 分母按 diff"因降级移出"对齐 → 锚点绊线（上 run 全过、本 run 全败且双方 trials≥2 且 mode 相同 → 标红）。
- `score <run>`：判定明细 JSONL + 能力/归因/用例质量视图（judge 不一致清单、变体泄露提示复核、found>1、forced 前提成立率偏低 ec）。

## 4. tools

- **p0-2-inventory.mjs**：`node tools/p0-2-inventory.mjs <session.v4.jsonl.zstd> --roots <dir,…> [-o skills-inventory.yaml]`。用 runner/lib/vendor/zstd 多帧解压 → 正则提取 `<available_skills>` 清单 → 对每个名称在各 root 与 CLI 安装目录中定位文件（frontmatter name 匹配）→ 输出 `{exported_at, agent_version?, roots: [{path, manifest_sha256}], skills: [{name, root, file, sha256}]}`；未定位到的记 `root: bundled?`。
- **p0-1-verify.mjs**：`node tools/p0-1-verify.mjs --profile <p> [--bin]`。步骤：复制权威根到临时目录并改一个 skill 的 description → 生成 overlay（customSkillDirs+includeDefaultRoots:false）→ 起一个 episode 发一句话 → 断言日志目录消息含改动后描述、不含其他根残留 → 并发第二个 episode（未改副本）互不可见 → 追加一次 forced `/skill名` 验证 `<skill_content>` 注入 → 输出 PASS/FAIL 明细与 ask_user 观察记录。真实请求由现场执行。
