# 评测配置重构方案：六份配置与七个模块

版本：v1.0（2026-10-28）· 基线：`feat/eval-gaps` d3c9310 · 状态：方案，待实施

本文先定义一条用例从编写到出分要经过哪些配置（§2），再用四轮评估检查新方案能否覆盖现有的全部配置项（§3），最后给出数据、代码、迁移和工作量（§4–§10）。

doc/13 界面设计 v1.0 是在旧的配置模型上设计的，在本方案定稿后需要按 §9 修订。

---

## 1. 结论摘要

**一条用例从写好到出分，依次经过 6 份配置：**

```
用例 ─① 用例配置─▶ ② 测法配置 ─▶ ③ 被测配置 ─▶ ④ 判定配置 ─▶ ⑤ 人工记录 ─▶ ⑥ 计分规则 ─▶ 结果
```

| # | 配置 | 回答的问题 | 改了以后 |
| --- | --- | --- | --- |
| ① | 用例配置 | 考什么：题面和标准 | 题面变了要**重跑**；标准变了要**重判** |
| ② | 测法配置 | 怎么考：用什么模式、跑哪些变体、锚点 | **重跑** |
| ③ | 被测配置 | 谁来答：模型、努力程度、agent、知识基底等 | **重跑**（产生新配置） |
| ④ | 判定配置 | 怎么判：每类条目用哪些算子 | **重判** |
| ⑤ | 人工记录 | 人怎么判 | 只影响被改的那几条 |
| ⑥ | 计分规则 | 怎么算分：权重、分值映射、否决、及格线、聚合方式 | **重算** |

另有三层辅助配置，**不参与结果的身份**：

- **执行参数**：并发、超时、续跑等，记在执行记录里；
- **用例规范**：编写时的校验规则和词表；
- **展示与工作流**：命名、默认配置、抽检比例、对比阈值。

**评估结论**（§3）：

- 现有 **73 个配置项全部有归属**。归入 6 份配置的 53 项，归入 3 层辅助配置的 19 项；另有 1 项（判定缓存）不是配置。
- 修补了旧模型的三个漏洞：
  - profile 内容改了但 id 没改，仍被当成同一个配置；
  - agent 版本和产品侧的 profile 文件不在配置身份里；
  - 改条目权重会被当成改期望，要重判。
- 有一处**行为变化**：模式改由测法决定，不再在执行时随意选择。

## 2. 目标模型

### 2.1 七个模块

| 模块 | 输入的配置 | 产出 | 代码位置 |
| --- | --- | --- | --- |
| 1 编写 | 用例规范（校验） | 用例 md、注入点定义 | `evalset/cases`、`evalset/knowledge` |
| 2 发布 | ① 用例配置、② 测法配置 | **评测集快照**：题面、标准、测法、条目权重初始值 | `md2case build` |
| 3 执行 | ③ 被测配置、执行参数、② 测法 | 执行记录（批次）、会话 | runner `skill-eval run` |
| 4 判定 | ④ 判定配置、① 标准 | 机器结论 | `scoring score / rejudge` |
| 5 复核 | 评审人 | 人工结论 | 复核服务 |
| 6 计分 | ⑥ 计分规则、有效结论（人工优先） | 会话分、会话结论 | `scoring rescore` |
| 7 汇总 | ⑥ 计分规则（聚合部分）、② 测法 | 变体分 → 用例分 → 维度分 → 综合分 | `views` |

### 2.2 身份与键

| 对象 | 键 | 由什么算出 | 与现状相比 |
| --- | --- | --- | --- |
| 题目（变体 × 题面） | `qkey = uid \| input_fp` | 提问、注入、主题、对话方式 | 不变 |
| 标准 | `standard_fp` | 可回答、前提、事实（id / 类型 / 文字 / 关键词 / 轮次 / 组）、路径 | **由 `judge_fp` 改来：去掉权重** |
| 评测集快照 | `evalset_version`（加上 `snapshot_sha`） | 各题目的 (`input_fp`, `standard_fp`)、测法、条目权重初始值 | 增加测法和权重初始值 |
| 测法 | `method_sha` | 见 §4.2 | **新增** |
| 被测配置 | `subject_fp` | 见 §4.3 | **新增**，取代 `CONFIG_ATTRS` |
| 执行记录 | `run_id` | — | 降为批次，不再是分析维度 |
| 会话 | `answer_id = run_id/uid-mode-t{trial}` | — | 不变 |
| 判定配置 | `chain_sha` | 算子实例和链，规范化后的哈希 | 不变 |
| 计分规则（全局部分） | `rules_sha` | 见 §4.6 | **由 `policy_sha` 改来**：测法相关的项移出 |
| 条目权重（按题目） | `weight_fp` | 题目各条目的有效权重 | **新增** |
| 会话结论 | (`answer_id`, `standard_fp`, `chain_sha`, `rules_sha`, `weight_fp`) | — | 键由 4 段变为 5 段 |

### 3.2 第二轮：新方案内部是否一致

逐条检查第一轮的映射，看新方案自身有没有矛盾。发现 9 处，处理如下：

| 编号 | 问题 | 处理 |
| --- | --- | --- |
| C1 | 原方案草稿把「计分变体」放在测法里，但它只影响聚合，改了只需重算，不该和「要重跑」的测法绑在一起 | `exclude_rewrites` 拆成两项：② 测法管**执行哪些变体**，例如诱导默认不跑；⑥ 计分规则管**哪些变体计分** |
| C2 | 禁止事实和路径也能写【权重】，配合否决方式 `weight` 时才起作用 | ⑥ 的条目权重覆盖所有条目类型；`veto=weight` 时用这份权重 |
| C3 | 组的计分规则写死在代码里，新方案如果不写明，会被误以为可配 | 在 ⑥ 里写明为固定规则；组的成员关系仍然属于 ① 标准 |
| C4 | 人工总分 `@total` 的 item_sha 存的是 `judge_fp`。权重移出之后，改权重就不会再让人工总分作废 | 人工总分是对整段对话的判断，与权重无关，**保留有效**；页面在它旁边提示「计分规则或权重已在人工总分之后修改」。作废条件改为 `standard_fp` 或回答变了 |
| C5 | 历史数据两种模式都有；改成由测法定模式之后，另一种模式的会话怎么处理 | 计分时按测法过滤；不属于测法模式的会话标为「诊断会话」，不计分，但可以在对比和诊断里查看。这就是原 `headline_mode` 的效果 |
| C6 | 测法改了模式，但还没有用新模式跑过的数据 | 汇总时显示「测法已变，缺少 forced 会话」，提示补跑，不回退去用旧模式的数据 |
| C7 | 被测配置的身份变成内容指纹，同一个 profile 改了一个与结果无关的字段（如 `description`）也会分裂 | `subject_fp` 只取 §4.3 列出的字段；其余字段（#24 描述、#37–#40）不计入 |
| C8 | 「当前期望」原来是逐题指针，新方案里由谁负责 | 「当前标准」= 当前快照里的 `standard_fp`；「当前权重」= 快照里的初始值，叠加 ⑥ 条目权重表里的修改。逐题指针保留，只在临时实验（例如对单题试新标准）时使用，页面上标「偏离快照」 |
| C9 | 维度清单在规范层，综合分是否「完整」却要用到它 | 维度清单仍以 `mapping.yaml` 为准；⑥ 只引用，不另存一份 |

### 3.3 第三轮：反向检查，新配置是否都有落脚点

逐份检查新配置是否同时具备身份键、存储位置、修改入口、版本记录和改动代价：

| 配置 | 身份键 | 存储 | 修改入口 | 版本记录 | 代价是否明确 |
| --- | --- | --- | --- | --- | --- |
| ① 用例配置 | `qkey`、`standard_fp`、`evalset_version` | md → dist → `specs`、`questions` | 改 md 后重新发布 | 快照 + git | 是 |
| ② 测法配置 | `method_sha` | `evalset/method.yaml` → 写进快照 → `snapshots` 表（新） | 改文件后重新发布 | 跟随快照 | 是 |
| ③ 被测配置 | `subject_fp` | profile 文件 + 执行快照 → `runs.subject_fp`、`answers.subject_fp`（新） | 改 profile，或执行时覆盖 | 每个执行记录一份快照 | 是 |
| ④ 判定配置 | `chain_sha` | `operators.yaml` → `chains` | 改文件后执行 `rejudge` | `chains` 表 | 是 |
| ⑤ 人工记录 | (`answer_id`, `item_id`) + 指纹 | `reviews` | 复核页 | 只追加 | 是 |
| ⑥ 计分规则 | `rules_sha` + 每题的 `weight_fp` | `scoring/rules.yaml` + `item_weights` 表（新） | 改文件后执行 `rescore`；权重在页面上改 | `rules` 表（新）+ `item_weights` 的历史行 | 是 |

**新方案引入的新问题**（旧模型里没有）：

| 编号 | 问题 | 处理 |
| --- | --- | --- |
| N1 | 历史会话没有 `subject_fp` | 迁移时用执行快照回填。缺 agent 版本或 profile 文件哈希的旧记录，按「未知」计算，指纹单独成组，并标「身份不完整」 |
| N2 | `judge_fp` 去掉权重后，几个旧版本可能合并成一个 `standard_fp` | 机器结论的条目内容不含权重，合并后取任意一份，结果都相同；被合并的版本里的权重，转成 `item_weights` 的历史行 |
| N3 | 结论的键多了 `weight_fp`，旧结论全部失配 | 迁移后执行一次 `rescore`，只重算，不调用算子 |
| N4 | runner 原来的 `--modes` 用户 | 保留参数，但改名语义：指定了模式就算「诊断执行」，执行记录上标「诊断」；不指定时按测法 |

### 3.4 第四轮：场景验证

逐个检查典型操作在新旧方案下的代价：

| # | 操作 | 走哪份配置 | 新方案 | 旧方案 |
| --- | --- | --- | --- | --- |
| 1 | 改提问措辞 | ① 题面 | 新题目，重跑 | 相同 |
| 2 | 改某条事实的文字 | ① 标准 | 重判 | 相同 |
| 3 | 改条目权重 | ⑥ | **只重算这一题** | 新期望版本，**要重判** |
| 4 | 改及格线或分值映射 | ⑥ | 重算 | 相同 |
| 5 | 换模型或努力程度 | ③ | 新配置，重跑 | 相同 |
| 6 | 改了 profile 内容，没改 id | ③ | **新配置** | **被当成同一个配置，数据混在一起** |
| 7 | 升级 agent 版本 | ③ | **新配置** | **区分不出来** |
| 8 | 知识库更新 | ③ 知识基底 | 新配置，加过期标记 | 相同 |
| 9 | 某个维度改用 forced | ② | 重跑；没跑之前提示缺数据 | 改口径就生效；没跑过 forced 时数据为空，不提示 |
| 10 | 让诱导变体也计分 | ⑥（计分变体）+ ②（执行范围） | 重算；没跑过诱导就提示补跑 | 改口径 |
| 11 | 接入模型算子 | ④ | 重判 | 相同 |
| 12 | 只信规则判的分，不采信模型给的分 | ⑥ 开关 | 重算 | **做不到** |
| 13 | 人工改判一条 | ⑤ | 重算这一段 | 相同 |
| 14 | 给某个配置补跑样本 | 执行 | 样本累加，分数自动合并 | 相同；但页面按执行记录分开展示 |
| 15 | 发布新快照，大部分用例没变 | ① | 没变的题目（`qkey` 和 `standard_fp` 都相同）直接复用会话和结论 | 相同；但评测集版本在配置身份里，配置会分裂，对比要特意放开 |
| 16 | 对比同一配置在两种模式下的表现 | 诊断执行 | 诊断会话，不进分数 | 两种模式都算正式数据，靠主模式取舍 |
| 17 | 调并发或超时 | 执行 | 不影响身份 | 相同 |

17 个场景都有明确的处理路径。其中 #3、#6、#7、#12 是新方案改善的地方；#9、#10 多了提示；#16 是行为变化。

### 3.5 评估结论

- **覆盖**：73 个现有配置项全部有归属，没有丢失任何能力。
- **改善**：
  - 被测配置的身份修了两个漏洞（#6、#7）；
  - 改权重不再触发重判（#3）；
  - 能控制是否采信算子给的分（#12）；
  - 评测集版本不再让被测配置分裂（#15）。
- **行为变化，需要确认**：模式由测法决定，手工指定的模式算诊断执行（#16、N4）。
- **代价**：一次 schema 迁移（v8），加一次全量 `rescore`；**不需要重跑，也不需要重判**。

## 4. 六份配置的定义

### 4.1 ① 用例配置

- **源文件**：用例 md 和 `knowledge/*.yaml`，格式不变。
- **发布**：`md2case build --version v… [--include admitted]`，产出评测集快照（dist jsonl 加快照头）。
- **题面**：计入 `input_fp`，规则不变。
- **标准**：计入 `standard_fp`。规则同现在的 `judge_fp_of`，**只是去掉 `weight`**。
- **权重**：md 里的【权重】在编译时写进快照的 `weights` 段，作为初始值，不计入任何指纹。

### 4.2 ② 测法配置（新增 `evalset/method.yaml`，随快照发布）

```yaml
schema: 1
modes:                      # 每个维度用什么模式（原 policy.headline_mode）
  default: natural
  错误知识纠正: forced
run_rewrites: [口语, 极简, 语序]   # 常规执行跑哪些改写；种子总是跑。诱导不在其中，默认不跑
anchors: [kr-0201#0, kr-0204#0, mt-0201#0]   # 原 runner/anchors.txt
```

`method_sha` = 上面内容规范化后的哈希，写进快照。runner 执行时读取快照里的测法来生成执行计划。

### 4.3 ③ 被测配置

`subject_fp` = 下列字段规范化后的哈希，由 runner 在执行时算出，写进 `run.json`：

| 字段 | 来源 |
| --- | --- |
| model、model_provider、reasoning_effort | profile，执行时覆盖则取覆盖值 |
| skills_mode、skill_tool、routing | profile |
| skills_base | 执行快照（实体技能根的清单哈希） |
| eline_profile 哈希、dsh.profile | 执行快照、profile |
| agent 名称和版本 | 执行快照 |
| adapter | CLI |

不计入 `subject_fp` 的字段：id、描述、路径类字段（bin、home、env、roots 路径）、timeout、budget、web.port 和 web.headless，以及全部执行参数。

展示名按以下顺序取：

1. `config_meta` 里起的名字；
2. 差异属性拼成的名字（规则见 doc/13 §2.3）；
3. profile id。

### 4.4 ④ 判定配置

`operators.yaml` 格式不变。

预留**组合算子**：几个子算子同时判同一条，按投票或阈值合并成一个结论。合并规则写在算子实例的参数里，计入 `chain_sha`。**判定配置里不设权重**，权重只出现在 ⑥。

### 4.5 ⑤ 人工记录

`reviews` 表不变。人工总分 `@total` 的作废条件改为：`standard_fp` 变了，或回答变了（§3.2 C4）。

### 4.6 ⑥ 计分规则（新增 `scoring/rules.yaml` + `item_weights` 表）

```yaml
schema: 1
pass_mark: 60
undecided: exclude          # exclude | fail
default_weight: 1
map: {对: 100, 部分: 50, 未提及: 0, 错: 0, 满足: 100, 违反: 0, 未采信: 100, 采信: 0, 拒答: 100, 未拒答: 0}
operator_score: adopt       # adopt：采信算子给的分 | ignore：只用 map
veto: {forbidden_adopted: zero, path_violated: zero, required_wrong: zero, cap: 40}
group: max                  # 固定规则：组分取组内最高分，组权重取最大；写在这里只作说明
aggregate:
  scored_rewrites_exclude: [诱导]   # 原 exclude_rewrites 中「不计分」的部分
  dimension_unit: case
  dimensions: {知识召回: 1, 多轮上下文召回: 1, 同义请求一致性: 1, 错误知识纠正: 1}
```

`rules_sha` = 上面内容规范化后的哈希。

**条目权重表** `item_weights(qkey, item_id, weight, percent, set_at, set_by, active)`：

- 有效权重 = 表里该条目最新的有效行，没有时取快照里的初始值，再没有时取 `default_weight`。
- `weight_fp` = 这一题全部条目有效权重的哈希。
- 页面上改权重时，只往这张表追加行，然后只重算这一题的结论。

`compare_delta` 移到结果对比页，作为展示参数，默认 10，不再写在计分规则里。

## 7. 迁移步骤

1. **备份**：执行 `scoring backup`。
2. **建表**：执行 v8 迁移，新建 `snapshots`、`item_weights`、`rules`，并给 `runs`、`answers` 加列。
3. **改写标准指纹**：对 `specs` 逐行重算 `standard_fp`，按新值合并重复行。被合并的行里的权重写进 `item_weights`：当前期望的权重作为有效行，其余作为历史行。同步改写 `verdicts`、`questions` 和 `spec_versions` 的键。
4. **回填被测指纹**：从 `runs.snapshot_json` 回填 `subject_fp`，缺失的字段按「未知」计算（§3.3 N1）。
5. **回填快照与测法**：已有的评测集版本，用当时的 policy（`headline_mode`、`exclude_rewrites`）和 `anchors.txt` 生成测法，写进 `snapshots`。
6. **生成计分规则**：由当前的 `policy.yaml` 生成 `rules.yaml`，写进 `rules`。
7. **重算**：全量 `rescore`。只重算，不调用算子。
8. **对拍验证**：在权重和口径都不变的前提下，迁移前后每段会话的分数和结论应完全一致；变体分、用例分、维度分、综合分也应一致。有差异的逐条列出。唯一允许的差异来自 §3.2 C5，即诊断会话被排除在外。

## 8. 兼容与风险

| 风险 | 应对 |
| --- | --- |
| 旧链接和 CLI 参数（`--policy`、`judge_fp`） | 保留一个版本的别名，并打印弃用提示 |
| 被测指纹拆得太细，配置数暴涨 | 迁移后列出各指纹的差异字段，确认没有无关字段混进来（§3.2 C7） |
| 测法改了模式，历史数据缺新模式的会话 | 汇总时提示「缺数据」，不用旧模式代替（§3.2 C6） |
| 人工总分在改权重后仍然有效 | 页面提示，由评审人决定是否重新给分（§3.2 C4） |
| 迁移中途失败 | 整个迁移在同一个事务里完成，先在备份上演练 |
