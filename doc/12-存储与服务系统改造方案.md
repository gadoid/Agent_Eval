# 12 存储与服务系统改造方案

v1（2026-10-24）· 基线 `main` 84c48b7 · 设计方案（不含实现）· 配合 doc/11（领域拆分与注册机制）

## 0. 现状与约束

| 方面 | 现状 | 对后续的限制 |
| --- | --- | --- |
| 评测库 | SQLite 单文件 `archive/eval.db`，WAL；`scoring/store.py` 是唯一访问模块（基线约 45 处 SQL），基本只用标准 SQL；按版本顺序迁移 | 单机、单写者；不能多人同时在线写；不能跨机器访问 |
| 大对象 | 完整 EpisodeRecord 以 JSON 存在 `answers.record_json`；原始运行产物（results.jsonl、run.json、会话日志）在 `runner/out/<run>/`；技能基底在 `.eval-skills/base` | 库体积随会话线性增长；日志与基底无身份、无版本、无访问控制 |
| 服务 | `python -m scoring serve`：单进程 FastAPI + Jinja，默认只听 127.0.0.1，无登录 | 不能多人用；无权限；页面与数据访问耦合在一个文件 |
| 计算 | 判定、重判、重算都在命令行进程内同步执行；模型算子会在命令行里直接调模型 | 无排队、无重试、无成本控制；不能分布到多台机器 |
| 执行 | runner 驱动 **ElineAI 桌面客户端**（Windows，`eline.exe` + 改造版 dsh），在本机运行 | 执行端必须是装有客户端的 Windows 机器，不能简单容器化 |
| 数据敏感性 | 评测库与日志含真实业务对话；仓库当前可匿名访问，`tests/fixtures` 含真实日志 | 服务化前必须先解决访问控制与脱敏 |

doc/09 §9 已定的演进方向保持不变：**不用 k-v 存储；多人在线复核时迁 PostgreSQL；分析变慢时引入 DuckDB**。本方案把这个方向具体化，并补上大对象存储、作业系统、服务拆分和执行节点。

| --- | --- | --- |

## 2. 存储设计

### 2.1 数据分类与载体

| 数据 | 例子 | 本地模式 | 服务模式 |
| --- | --- | --- | --- |
| 业务元数据与结果 | 对象、用例、评测集版本、run、答案索引、判定、复核、结论、指标值、注册项、作业 | SQLite | **PostgreSQL** |
| 大对象（不可变） | EpisodeRecord 全量、会话日志、上传包、技能基底、物化快照、导出文件 | 本地目录（按内容哈希分目录） | **对象存储**（S3 兼容，如 MinIO） |
| 分析数据 | 指标宽表、对比与贡献计算的输入 | DuckDB 读 SQLite / Parquet 导出（可选） | DuckDB 读 Parquet 快照；或 PostgreSQL 物化视图 |
| 作业队列 | 待执行/执行中的作业 | SQLite 表 | PostgreSQL 表（`FOR UPDATE SKIP LOCKED`），不引入额外消息中间件 |
| 判定缓存 | 模型算子结果 | 评测库表（现有） | 同左 |

**原则**：
- 关系库只存可查询的结构化数据和对大对象的引用；大对象一律**内容寻址**（sha256），写入后不可变，库里存 `blob_ref = sha256 + 大小 + 类型`。
- 原始层「文件不可变」的原则（doc/09 §6.1）推广为「大对象不可变」：本地模式就是本地目录，服务模式换成对象存储，逻辑一致。
- 分析只读：DuckDB 不写业务数据，失效可随时重建。

### 2.2 逻辑模型（按领域）

在 doc/09 表结构基础上调整，标 ★ 的为新增，△ 为修改：

| 领域 | 表 | 说明 |
| --- | --- | --- |
| 被测对象 | ★`subjects`(subject_id, type, name, owner, visibility) · ★`subject_versions`(version_id, subject_id, version, content_sha, manifest_json, blob_ref, status, created_at) | 上传与仓库内对象同一模型；`status`：uploaded / checked / rejected / active |
| 用例 | `questions`、`specs`、`spec_versions`（现有）· ★`suites`(suite_id, version, definition_json) · ★`suite_members` | 套件按 doc/11 R10 登记 |
| 执行 | △`runs`（加 `submission_id`、`node_id`）· ★`run_bindings`(run_id, subject_version_id, role) · △`answers`（`record_json` → `record_ref` + 抽取列：轮数、状态、耗时、token） | 绑定记录这次 run 装了哪些对象版本；全量记录进大对象存储 |
| 判定 | `verdicts`、`verdict_cache`（现有，加 `score`） | — |
| 评分 | ★`measures`(answer_id, metric_id, metric_ver, scope, turn, value_num, value_text, source, config_sha) · △`conclusions`（键加 `rubric_sha`；加分数列） | doc/10、doc/11 |
| 复核 | △`reviews`（`reviewer` → `user_id`；加 `score`） | 评审人从自报变为登录身份 |
| 注册 | ★`registry_items`(kind, item_id, version, sha, manifest_json, source) | doc/11 §3.1 |
| 作业 | ★`jobs`(job_id, type, payload_json, idem_key, status, attempts, lease_until, node_id, cost_json, error, timestamps) · ★`submissions`(submission_id, subject_version_id, suite_ids, rubric_id, owner, status, budget_json) | §3.4 |
| 平台 | ★`users`、★`tenants`、★`memberships`(role) · ★`audit_log`(who, action, target, at, detail) | 服务模式；本地模式只有一个本地用户 |

**`answers.record_json` 外置**是体积上最关键的一步：会话全量记录占库体积的绝大部分。外置后库里只留抽取列（复核与统计用到的字段），全量记录按需从大对象存储取（复核页一次只读一段）。

### 2.3 访问层：按领域的仓储接口

`store.py` 已是唯一访问模块，按领域拆成仓储接口，每个接口两种实现：

```python
class AnswerRepo(Protocol):
    def ingest(self, record_ref: BlobRef, extracted: dict, run_id: str) -> str: ...
    def get(self, answer_id: str) -> AnswerRow | None: ...
    def list_for_question(self, qkey: str) -> list[AnswerRow]: ...

class BlobStore(Protocol):
    def put(self, data: bytes, media_type: str) -> BlobRef: ...      # 内容寻址，重复写入幂等
    def get(self, ref: BlobRef) -> bytes: ...
```

| 决策点 | 方案 |
| --- | --- |
| SQL 访问 | 采用 SQLAlchemy Core（不用 ORM）统一 SQLite 与 PostgreSQL；查询仍按领域写在仓储里，业务代码不拼 SQL（延续 doc/09 §9） |
| 迁移 | Alembic 管理两种方言的迁移；现有 v1–v4 迁移冻结为基线，之后的变更都走 Alembic |
| 事务 | 工作单元（Unit of Work）：复核批量提交、作业领取等跨表操作在一个事务内完成 |
| 依赖 | 命令行路径新增 SQLAlchemy 依赖（目前只依赖标准库与 PyYAML）——见 §6 待定 |

### 2.4 生命周期、备份与隐私

| 项 | 本地模式 | 服务模式 |
| --- | --- | --- |
| 备份 | `backup`（SQLite 原生）+ 大对象目录复制 | PostgreSQL 时间点恢复（PITR）；对象存储开版本与生命周期策略 |
| 保留期 | 不限 | 按数据分级：真实会话日志 N 天后归档或脱敏；上传包随对象下线保留 M 天；指标与结论长期保留 |
| 访问控制 | 文件系统权限 | 按租户与角色；真实业务对话仅评审与负责人可见；对外报表只含聚合数据 |
| 脱敏 | — | 入库时可选脱敏管道（客户名、单号等字段替换），原文仅存受限桶 |
| 审计 | — | 复核、手改会话分、上传、权限变更写 `audit_log` |

### 2.5 从现有评测库迁移

一次性工具 `python -m scoring migrate --from sqlite:///archive/eval.db --to postgresql://… --blobs s3://…`：

1. 冻结写入（只读打开源库）。
2. `answers.record_json` 写入大对象存储，回填 `record_ref` 与抽取列。
3. 其余表按批复制；`reviews.reviewer` 按映射表转为 `user_id`（未匹配的保留原文到 `reviewer_label`）。
4. 校验：各表行数、每段答案的 `answer_sha` 与条目 `item_sha` 重算一致、抽样比对结论。
5. 切换：本地评测库保留为只读备份。

## 3. 服务设计

### 3.1 组件

```
               ┌──────────── 浏览器（复核、报表、上传） ────────────┐
               ▼                                                    │
        ┌─────────────┐   REST/JSON   ┌──────────────┐              │
 CLI ──▶│  API 服务    │◀────────────▶│ PostgreSQL    │              │
        │（无状态，可多 │              └──────────────┘              │
        │  实例）+ Web │◀────────────▶┌──────────────┐              │
        └──────┬──────┘   预签名链接   │ 对象存储       │◀─────────────┘
               │ 作业入队              └──────┬───────┘
               ▼                              │
        ┌─────────────┐ 领取/心跳/回报 ┌───────┴────────────────────────┐
        │ jobs 表      │◀─────────────▶│ 工作进程                         │
        └─────────────┘               │  · 判定 worker（规则 + 模型算子） │
                                      │  · 评分/聚合 worker              │
                                      │  · 静态检查 worker（上传包）      │
                                      │  · 执行节点 agent（Windows +      │
                                      │    ElineAI 客户端，拉取会话作业）  │
                                      └──────────────────────────────────┘
```

| 组件 | 职责 | 技术 |
| --- | --- | --- |
| API 服务 | 全部领域操作的唯一入口：对象与上传、套件、提交与作业、答案、复核、结论、报表、注册项；鉴权 | FastAPI（沿用），无状态，OpenAPI 文档 |
| Web | 复核、用例、对比、判定质量页面（doc/10）；上传与提交页面（P3） | 沿用服务端渲染 + 少量原生 JS（doc/10 不引入构建链）；页面只调 API，不直接访问库 |
| 作业系统 | 作业入队、领取、租约、重试、取消、预算 | PostgreSQL 表 + `SKIP LOCKED` |
| 判定 worker | 执行判定链；模型算子的并发、限速、超时、费用统计；判定缓存 | Python（复用 judging 域代码） |
| 评分/聚合 worker | 重算结论、计算指标、导出 Parquet、预计算报表 | Python |
| 静态检查 worker | 上传包的清单校验、格式、禁用内容、权限声明 | Python；只读处理，不执行上传代码 |
| 执行节点 agent | 在装有 ElineAI 客户端的 Windows 机器上常驻；领取会话作业 → 物化对象 → 驱动客户端 → 上传记录与日志 → 回报 | Node（复用 runner），新增作业协议客户端 |
| CLI | 本地模式：直接调用领域代码（现在的用法）；服务模式：作为 API 客户端 | 同一套命令，`--server` 切换 |

### 3.2 两种部署形态

| | 本地模式 | 服务模式 |
| --- | --- | --- |
| 评测库 | SQLite | PostgreSQL |
| 大对象 | 本地目录 | 对象存储 |
| 作业 | 进程内顺序执行（等价于现在的命令行行为） | 作业表 + worker + 执行节点 |
| 鉴权 | 无（本机单用户） | SSO / OIDC，角色与租户 |
| 适用 | 用例作者调试、离线评测、CI | 团队复核、正式评测、上传测评 |

两种形态共用领域代码与仓储接口，差别只在配置选择的实现（`backend: local | server`）。本地模式必须持续可用，保证不依赖服务也能完成编写→执行→判定→复核。

### 3.3 API 概要

| 资源 | 主要接口 |
| --- | --- |
| 对象 | `POST /subjects`（上传，返回预签名上传链接）· `GET /subjects/{id}/versions` · `POST /subject-versions/{id}/check` |
| 套件与用例 | `GET /suites` · `POST /evalsets`（导入编译产物）· `GET /cases/{case_id}` |
| 提交与作业 | `POST /submissions`（对象版本 + 套件 + 评分方案 + 预算）· `GET /submissions/{id}` · `GET /jobs?status=` · `POST /jobs/{id}/cancel` |
| 执行节点 | `POST /nodes/lease`（领取作业）· `POST /jobs/{id}/heartbeat` · `POST /jobs/{id}/result`（记录引用 + 摘要） |
| 答案与复核 | `GET /answers/{id}`（含记录的按需读取）· `POST /answers/{id}/reviews`（批量）· `POST /answers/{id}/reviews/preview` |
| 结果 | `GET /conclusions` · `GET /reports/case/{id}` · `GET /reports/compare` · `GET /reports/subject/{version_id}` |
| 注册项 | `GET /registry?kind=` · `POST /registry`（仓库级，限管理员） |

doc/10 的 `/api/review/preview`、`/api/reviews` 即其中复核接口的本地版本，路径在服务模式下归并到上表。

### 3.4 作业模型

| 作业类型 | 输入 | 输出 | 执行者 |
| --- | --- | --- | --- |
| `static_check` | 对象版本 | 检查报告、状态 | 静态检查 worker |
| `plan` | 提交（对象 + 套件 + 对照设计） | 会话作业列表 | API 内同步或 worker |
| `execute` | 一段会话（用例行、模式、trial、绑定的对象版本） | EpisodeRecord、日志（大对象） | 执行节点 |
| `judge` | 答案 + 判定配置 | 判定行 | 判定 worker |
| `score` | 答案 + 评分方案 | 指标值、结论 | 评分 worker |
| `aggregate` | 提交或评测集 | 报表快照、Parquet | 评分/聚合 worker |

- **状态机**：queued → leased → running → succeeded / failed / cancelled；租约到期未心跳则回到 queued；失败按退避重试，超过次数记 failed。
- **幂等**：`idem_key` = 作业类型 + 输入指纹（如判定作业 = answer_id + judge_fp + chain_sha）。重复入队直接返回已有作业；与现有「只补缺」的语义一致。
- **依赖**：execute 成功后自动入队 judge，judge 后入队 score，提交下所有 score 完成后入队 aggregate。
- **预算**：提交级预算（会话数、token、费用上限）；超出时停止派发并标记提交为「预算耗尽」。

### 3.5 执行节点与隔离

执行依赖 ElineAI 桌面客户端，执行节点是 Windows 机器：

| 被测内容 | 隔离方式 |
| --- | --- |
| 仓库内用例、可信 skill | 现有方式：每段会话物化独立副本（bundled-copy），节点常驻 |
| 上传的 skill（纯内容） | 同上，另加：副本目录只读挂载、会话结束即删除；节点不保存任何凭据之外的数据 |
| 上传的插件（含代码） | 一次性 Windows 虚拟机或 Windows Sandbox：每个作业从干净快照启动，结束即销毁；出站网络白名单；只放测试账号凭据 |

节点注册时声明能力（客户端版本、可运行的隔离级别、并发数）；作业按所需隔离级别派发。客户端版本进入运行快照（现有 `snapshot`），版本不一致的结果不混比。

### 3.6 可观测性与成本

- 结构化日志带 `job_id`、`submission_id`、`node_id`。
- 指标：队列长度、作业时延、失败率、节点在线数；模型算子调用次数、token、费用（按提交与租户累计）。
- 报表页面显示每个提交的费用与耗时；超预算告警。

### 3.7 安全

| 项 | 措施 |
| --- | --- |
| 身份 | SSO / OIDC；角色：管理员、评测负责人、用例作者、评审人、上传者 |
| 不可信内容 | 上传包只在静态检查 worker（不执行）和隔离执行环境中处理；API 与 worker 不执行上传代码 |
| 凭据 | 执行节点只持有测试账号；模型 API 密钥只在判定 worker；统一由密钥管理服务下发 |
| 数据 | 真实会话按租户与角色控制可见性；对外报表只含聚合；仓库转为私有并清理 fixture 中的真实日志（讨论纪要 §4.3） |

## 4. 演进路线（与 doc/11 对齐）

| 阶段 | 存储 | 服务 | 对应 doc/11 | 触发条件 |
| --- | --- | --- | --- | --- |
| **S0 访问层拆分** | `store.py` 按领域拆成仓储接口；引入 `BlobStore`（本地目录实现），`record_json` 外置；`measures`、`registry_items` 表 | 不变（本地 serve） | P0 | 现在，随 P0 一起做 |
| **S1 作业化（本地）** | `jobs` 表（SQLite）；判定、评分改为作业，本地进程内 worker 消费 | 命令行改为「入队 + 本地执行」；执行节点协议定义完成（同机运行） | P1–P2 | 评测规模上来、需要并发或重试时 |
| **S2 服务化** | PostgreSQL + 对象存储；Alembic 迁移；一次性迁移工具 | API 服务 + Web + worker + 执行节点 agent；SSO；审计 | P3 | 多人在线复核，或开放上传测评前 |
| **S3 分析** | Parquet 快照 + DuckDB；必要时物化视图 | 报表预计算 | P3 之后 | 分析查询变慢（doc/09 §9 的触发条件） |

S0、S1 不改变部署形态，可以先在单机上完成全部结构调整；S2 才引入新的基础设施。
