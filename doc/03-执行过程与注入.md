# 执行过程与注入（链路 2 / 3）

版本：v3.2（2026-10-22）

## 1. 范围与职责

执行器（沿昨日 skill-eval-runner 架构）把一个编译产物版本变成一组带环境快照的会话结果。职责边界：

| 执行器做 | 执行器不做 |
|---|---|
| 读取并筛选评测集、按能力规划会话 | 解析 md（编译已完成）、判定与打分 |
| 指令注入（forced）与知识注入的运行期物化 | 修改原始 skill（永远只读） |
| 逐轮驱动 ElineAI CLI、超时与进程树清理 | 失败重试（只做 trials 独立采样） |
| 逐轮观测（回答、工具调用、skill、用量） | 检索过程与忠实度分析 |
| 装配 EpisodeRecord、断点续跑 | 报表与结论 |

## 2. 输入

**编译行**（`dist/evalset-<ver>.jsonl` 的一行，schema 2）。执行器只读取 5 个字段：`uid`、`dim`、`history`、`turns`、`injections`；规划器在 forced 干预下另外读取 `topic`（routing 映射）与 `path`（只检查 forced 目标是否被 `禁止`），不影响会话执行。其余字段（conditions、preconditions、facts、path、evidence、tags、reference_answer…）不读取，原样内嵌进结果行随行带出（见 [04](04-采集与结果装配.md)）。

**Profile**（`runner/profile.eline.yaml`）：

```yaml
id: eline-glm53-field        # 写入环境快照
model: glm-5.3               # 仅记录，实际模型由 ElineAI profile 决定
dsh:
  bin: node <npm>/@deepseek-ai/dsh/lib/bin.js   # ElineAI 的 dsh 兼容 CLI
  profile: evalheadless      # ElineAI 侧 profile（模型、平台 origin 等）
  profile_files:             # 快照 eline_profile 的兜底哈希清单（CLI 无法输出解析后 profile 时，method: files）
    - ~/.eline/profiles/evalheadless/cordis.patch.yml   # 只列配置文件，不含 node_modules、lockfile
  timeout_ms: 600000
budget:                      # 可选；dry-run 估算超出时提醒，不阻断
  max_tokens: 5000000
  max_hours: 4
skills_roots:                # 评测基底：按 P0-2 盘点结果填写（生产可见的全部 skill 根）；本 run 唯一的 skill 来源
  - ~/.eline/skills          # 用户根
  # - <内置 skill 根>        # 盘点确认内置 skill 参与路由时加入
skills_inventory: runner/skills-inventory.yaml   # 盘点结果，含同名 skill 的生效来源
skill_tool: skill            # skill 加载工具名，随版本可调
routing:                     # topic → skill，供 forced 指令注入
  进单资料审核: [trade-documents]
web:                         # web-ui 备通道（可选）
  home: ~/.eline-eval
  port: 3081
```

## 3. S6 规划：筛选与展开

`uid × 干预 × trial` 一段会话（Episode）。规划器做四件事：

0. **环境检查**：计算环境快照；比对盘点记录（agent 版本、默认根 skill 清单哈希），不一致提示"inventory 过期"（[01](01-业务过程总览.md) 第 2 节）。
1. **筛选**：`--dims`、`--only <uid…>`、topic 过滤。锚点（`runner/anchors.txt`）只在**全量 run**（未指定 `--only`/`--dims`/topic 过滤）时默认纳入，在 run.json 中单独标记；调试单条用例时不带锚点，避免白付成本。`--anchors on|off` 可显式覆盖默认行为。锚点 uid 不在当前 dist 中时，在计划中提示。**锚点的 trials 固定取 max(N, 2)**，保证绊线不在单次采样上触发。
2. **能力适配**：执行器做不到的在此跳过并写明原因（进 run.json），不在运行时悄悄降级——
   - `history: prefill` 且当前适配器不支持预置历史（CLI 通道即如此）；
   - forced 干预下用例没有 topic 或 routing 无映射；
   - forced 干预下 routing 映射到的 skill 恰是该用例路径中 `禁止` 加载的 skill（配置与用例冲突，跳过 forced，保留 natural）；
   - 前置条件 P0-1/P0-2 未完成时的 ec 用例（见 [01](01-业务过程总览.md) 第 2 节；原因 `isolation-not-verified`）；
   - 用例引用的注入点在基底中无对应文件；
   - **注入预演未命中**：对基底只读地预演每条注入的 key 匹配，`found = 0` 的用例跳过（原因 `injection-key-missed`），`found > 1` 进计划的提示清单。预演不写文件，与 check `--docs` 同口径，弥补"run 时 skill 版本晚于最近一次 check"的窗口。
3. **展开**：按 `--modes natural,forced --trials N` 生成 Episode 计划。

`--dry-run` 打印完整计划（会话数、跳过项及原因、预演命中次数、inventory 是否过期），是第 3 道门禁：计划确认后才投入真实请求。

**成本估算**：dry-run 同时给出一行估算——计划总轮数 × 上一次同 Profile run 的每轮平均 token 与平均耗时（÷ 并发数），得到预计总 token 与预计时长；超过 Profile `budget` 时提醒，不阻断。没有历史 run 时只显示会话数与总轮数。

## 4. 「结构化可执行用例」的两级转换

用例从 md 到可执行会话分两级，语义各管一段：

| 级别 | 发生在 | 做什么 | 产物 |
|---|---|---|---|
| 编译期结构化（静态） | S5 build | 变体展开为 `turns[]`、注入引用解析为可物化操作、随行字段带出 | dist 行（uid 粒度） |
| 运行期结构化（动态） | S6/S7 plan | dist 行 × 干预 × trial → Episode 计划；每段会话物化独立工作目录（skill 副本、overlay、workspace） | `.work/<episode>/`（会话粒度） |

执行器对 md 零解析；对 dist 行也只消费 5 个字段——两级转换都不产生"第二个数据源"。

## 5. 注入执行

两类注入对应链路 2 中「指令注入」与「配置文件内容注入」：

### 5.1 指令注入（forced 干预）

- Profile 的 `routing` 把用例 `topic` 映射到 skill；forced 模式在**第一轮用户消息前**追加 `/skill名`，由 ElineAI 确定性注入（非工具调用）。
- natural 模式不注入，观察模型能否自发加载 skill。
- 同一 uid 的 natural/forced 对比是归因的**近似**依据，不是严格对照：forced 的 skill 内容以用户命令语义进入上下文，natural 经工具结果进入，两者在上下文中的位置与角色不同。因此归因先看 natural 会话自身的加载信号（未加载 / 误加载 / 加载但答错），forced 结果只作为"知识可用性"的参照，判定口径见 [04](04-采集与结果装配.md) 第 6 节。

### 5.2 知识注入（运行期物化）

CASE-STRUCTURE 规定：knowledge 只定义"改什么"，注入只作用于单个 episode 的 skill 副本，原始 skill 只读。

**环境对称原则**：所有会话——无论有无注入、无论 natural 还是 forced——走同一套物化与接线，唯一差别是副本上是否做了替换。否则 ec 与 kr/mt 会在不同的 skill 目录下运行，路由候选集不同，维度间不可比。

**生效条件**：本节的物化与接线以前置条件 P0-1（隔离机制验证）与 P0-2（skill 盘点）完成为前提（[01](01-业务过程总览.md) 第 2 节）。完成之前：kr/mt/sc 在 ElineAI 默认 skill 配置下运行，不物化副本；ec 在规划期跳过；环境快照记 `skills_mode: default-roots`，会话不写 `skills_sha256`。这样未验证的机制不会成为任何会话的必经路径，过渡期结果也不会被误当作同一基线对比。

物化过程：

1. **副本**：Episode 准备阶段，把基底（`skills_roots` 所列各根）复制到 `.work/<episode>/skills/<根序号>/`（当前用户根为 21 个平铺 md，量级 KB，全量复制保证无隐式共享）。多个根中存在同名 skill 时，按 `skills_inventory` 记录的生效来源只保留生效的那一份，使副本中不存在同名冲突，生效结果不依赖目录顺序。**所有会话都物化副本**；无注入的会话即原样副本，跳过第 2、3 步。
2. **替换**：逐条应用编译行 `injections[]`——对 `file` 做 `key → value` 的**精确字符串替换**（非正则、不忽略空白、替换文件中所有匹配位置；value 为空即删除）。当前 skill 形态为平铺 `<name>.md`，knowledge 的 `file` 约定相对 skill 根书写（如 `trade-company.md`），目录 bundle 形态（`<name>/SKILL.md`）同样支持。
3. **校验**：每条注入记录 `found`（key 命中次数）。`found = 0` 视为注入点漂移——该 Episode 直接判 `error`（原因 `injection-key-missed`），**不降级为无注入运行**。这是防止"假 ec 题"的第三道防线（前两道是 check `--docs` 与规划期预演；正常情况下预演已把这类会话挡掉，运行期仍出现说明基底在 run 中途被改动，应作为环境问题排查）。`found > 1` 不阻断，如实记录。
4. **接线**：在 episode 的 `overlay.patch.yml` 中追加 skill 提供方配置，把 skill 根指向副本（所有会话一致）：

```yaml
# overlay.patch.yml（与会话落盘重定向同层）
- id: skill-filesystem
  name: '@deepseek-ai/dsh-skill-filesystem'
  config:
    includeDefaultRoots: false            # 隔离：本会话只见副本（副本已包含盘点出的全部生产可见 skill）
    customSkillDirs:
      - "<out>/.work/<episode>/skills/0"
      - "<out>/.work/<episode>/skills/1"  # 每个基底根一项
```

5. **留痕**：副本物化（及替换）后计算一次 sha256，写入 EpisodeRecord 的 `skills_sha256`；注入的 `point/option/rev/found` 写入 `injections_applied`。无注入会话的副本 sha256 应等于环境快照中的 `skills_base`，不等即说明复制出错或基底在 run 中被改动，store 在 run.json 中告警。

> 前置条件 P0-1：`customSkillDirs` + `includeDefaultRoots: false` 经 `--patch` 按 episode 生效（配置项见 dsh-skill-filesystem 文档，与昨日已验证的 `session-persistence-jsonl` 落盘重定向同一 overlay 机制）。不通过时的退路：per-episode 独立 `DSH_HOME`（复制 profiles + 换 skills）；退路**同样未验证**，启用前按 P0-1 的同一方法验证一次。

## 6. Episode 生命周期

一段会话 = 准备 → 逐轮 → 收尾：

1. **准备**：分配 `.work/<序号>-<uid>-<干预>-t<trial>/`；物化 skill 副本并按需注入（5.2）；写 overlay（会话落盘重定向到本目录 `session/`，叠加 skill 根重定向）；开启会话。
2. **逐轮**（live，默认）：驱动器给出本轮用户消息 → 指令注入改写（仅 forced 首轮）→ 发送给 ElineAI → 探针观测本轮。**任何一轮状态非 ok 即停止该会话**，`failed_turn` 记录失败轮次；`send` 不抛异常，失败体现在 status（ok / incomplete / timeout / error）。error 带原因码；能从 CLI 输出或日志识别出平台限流（如 429）时，原因码记为 `rate-limited`，与其他错误分开统计。
3. **收尾**：组装 EpisodeRecord 追加到 `results.jsonl`；整段会话结束后删除 workspace（`--keep-workspace` 保留）。

多轮约束（沿昨日已验证口径）：同段会话共用一个 workspace 与 overlay（续接要求工作目录与持久化位置不变）；多轮为 2–5 轮；`prefill` 在规划阶段跳过。

## 7. ElineAI CLI 请求模型（链路 3）

### 7.1 主通道：dsh-cli 适配器（2026-10-22 起驱动 ElineAI 自带链路）

**评测必须驱动目标自己的改造版 dsh，不脱离 ElineAI 服务链路**（评测负责人的明确口径）。执行链路：

- bin = `D:/eline-ai/eline.exe --expose-internals <app.asar>dsh/.../dsh-desktop-host/lib/cli.js`（ElineAI 客户端自带的改造版 dsh，实测版本 0.2.0-rc.6；npm 的通用 dsh 仅作应急备份）
- env：`ELECTRON_RUN_AS_NODE=1`（eline.exe 以 Node 模式执行 asar 内 CLI）、`DSH_HOME=~/.eline`（账号凭据）、`DSH_BUNDLED_SKILL_DIR=<asar>/dsh-web-app/skills/trade-expert`（产品 21 个外贸 skill 的单一事实源，随产品版本，零拷贝）
- profile `evalheadless`（dsh-base + dsh-headless）+ 产品 persona：`dsh-persona` 的文案复制自产品 `trade-expert` preset（外贸专家人格与板块路由指引）；`tool-ask-user` 预设为 timed 60s
- 平台 `elineai.21eline.com`（provider deepseek-account，模型 glm-5.3）；协议、session 机制同 `@deepseek-ai/dsh`。适配器进程模型沿昨日已验证口径：

- **每轮一个进程**：第一轮 `<bin> evalheadless --patch overlay.patch.yml "<消息>"`；第二轮起追加 `--session-id <id>` 续接已持久化会话。
- **已知限制**：产品 skill 根在 asar 虚拟目录内——纯 Node 工具（盘点/物化/哈希）读不到 asar，P0-2 盘点刷新与 isolated 物化需经 `ELECTRON_RUN_AS_NODE` 的 eline node 执行或先导出实体目录；版本升级（如 rc.6→rc.7）需重验本节链路与 skill 根路径。
- **bundled-copy 模式（P0-3 结论，2026-10-23）**：overlay 在 rc.6 无效、复制 home 被凭据阻断后验证的第三条路线——`tools/export-skills.mjs`（经 eline node）把 asar 内产品技能根导出为实体基底，每段会话按 5.2 物化副本并经逐会话 env `DSH_BUNDLED_SKILL_DIR` 指向它（spawn 时叠加，并发安全）。产品链路实测：反转注入内容真实进入 `<skill_content>`。ec 维度在此模式下纳入规划。
- **会话 id**：取自日志的父会话目录名（`session-<uuid>`）；取不到时读 header 行，仍取不到则第二轮明确报错。
- **日志只追加**：每轮结束解压全文、只取上一轮之后的新增行交给解析器，因此每轮的回答、工具调用、skill、用量都只属于本轮。
- **超时**：进程树整体 kill（`killProcessTree`），该轮记 timeout。
- 指令注入的 `/skill名` 写在 prompt 前部，由 ElineAI 以用户命令语义注入。

### 7.2 备通道：web-ui 适配器（真实 UI）

起一个 dsh web 服务（独立 `DSH_HOME`，如 `~/.eline-eval`），无头浏览器驱动真实 UI 发送消息；观测读 web 服务原生落盘的 session 日志。用于评估"真实交互形态"下的表现，与 CLI 通道结果以环境快照的 `agent` 键区分。

现场经验（昨日验证，dsh 0.2.0-rc.2，进入本设计的默认约定）：

- web 通道 profile 的 `tool-ask-user` 必须 `mode: timed`（60s 自动放行），否则无人值守评测会挂住；CLI 通道待确认同款问题。自动放行时返回给 agent 的内容（空回复 / 固定文案）需在现场确认并写入 run.json，因为它会改变 agent 后续的回答；ask_user 本身作为观测信号采集（7.3）；
- 首屏预览/API Key 引导弹窗由适配器自动关闭；
- `mirror_sessions`（向客户端会话树镜像日志）停用——该客户端版本不容忍外来会话；如需人工审阅对话，用 web 服务原生落盘双端可见，或另镜像到非客户端目录。

### 7.3 观测信号（链路 3 → 链路 4 的接口）

轮次结束判定与四类探针全部来自 session 日志解析（vendor 内核，zstd 多帧解压 + 事件解析）：

| 信号 | 日志来源 |
|---|---|
| 本轮回答 | assistant 消息（含流式聚合） |
| 工具调用与结果 | 工具调用事件，按 callId 关联结果 |
| skill 加载 | 名为 `skill` 的工具调用（参数 name）+ 成功结果中的 `<skill_content name="…">`；forced 注入不是工具调用，单独记录 `forced_skills` |
| 用量 | 每轮 usage 事件（token、耗时另由执行器计时） |
| 反问 | 名为 ask_user 的工具调用及其放行结果（次数、是否自动放行） |
| 模型标识 | usage / response 事件中的模型字段（日志中存在时）；逐轮记录，run 结束汇总进环境快照 `models_observed`，用于发现远端模型漂移 |

反问与模型标识两项归入现有探针（工具探针、用量探针）输出，不新增探针类型；日志中不存在模型字段时记 `null`，不阻断。

注意：ElineAI 的 skill 路由只依据 name + description（截断 500 字符），`whenToUse` 不进目录——`细节` 级问题触发不到 skill 时，归因落在 skill 描述而非用例。

## 8. 并发、续跑与退出码

- **并发**：`--concurrency N`，每段会话独立目录与进程树，本地互不共享。服务端串扰无法在本地隔离，也不做一次性验证；锚点跨 run 不稳定时把它列为怀疑项之一（01 第 10 节 #5）。
- **续跑**：`--resume` 复用已有 `out/` 目录，已完成会话跳过；重新计算环境快照，evalset、runner_profile、eline_profile、skills_mode、skills_base 任一与已有 run.json 不同即拒绝续跑；旧 schema 结果同样拒绝。
- **trials**：同一 uid × 干预采样 N 次独立会话；不提供失败重跑（重跑会高估能力）。
- **一次运行一个 Profile**：比较配置 = 跑两次、离线配对比较。
- **退出码**：`0` 完成；`1` 参数/配置/评测集错误或找不到 CLI；`2` 完成但 error+timeout 占比超 `--max-error-rate`（默认 0.2）——结果产出但标记不可直接采信。
- **inspect 子命令**：对 `.work/<episode>` 导出日志事件类型、工具调用、skill 信号，供现场排查与 7.3 类信号的版本回归。

## 9. 与昨日实现的差异清单

| 项 | 昨日 | 本设计 | 动作 |
|---|---|---|---|
| 注入物化 | 无（接口预留） | 5.2 节全流程，所有会话统一物化与接线（以 P0-1/P0-2 为前提） | EpisodeRunner 准备阶段新增 skill 副本/替换/接线步骤 |
| 规划期注入预演 | 无 | 只读预演 key 命中，found=0 跳过 | planner 新增一个检查步骤（复用替换函数，不写文件） |
| 执行器读取字段 | 含 assistant_refs、topic、granularity | 收敛为 5 字段；topic 仅 forced 规划用；path 仅用于 forced/禁止冲突检查 | planner 微调 |
| 结果内嵌编译行 | 否 | EpisodeRecord 增加 `case` 字段 | store 装配时写入 |
