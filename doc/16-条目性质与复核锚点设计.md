# 条目性质与复核锚点设计

版本：v1.1（2026-10-28 评审修订）· 基线：`feat/eval-gaps` 804ed02 · 状态：P0 已实施（2026-10-28，验收全绿：Python 238 + Runner 67，存量指纹/改判零变化）

本文回答两个问题：

1. **条目性质**：事实条目怎么区分「客观」与「主观」。这个属性越早进模板越好，本期就要落地。
2. **复核锚点**：后期由模型生成复核导读、由人做判据级标注时，这些标记怎么挂回用例条目，以及条目或回答变化后，怎么判断标记是否仍然有效。本期只定契约和 ID 规则，不建表、不做页面。

讨论来源：2026-10-28 讨论纪要（主客观属性 → 复核导读 → 可解释判定 → 分期）。

---

## 1. 背景

知识分两种：

- **有唯一可核验答案的**：例如「非闰年 365 天」「我司报关需提供入货通知」。
- **合理表述不止一种的做法或建议**：例如「报价单最好注明付款方式」。

两者判「部分」的尺度不同，给分的语义也不同。现行结构里，事实只有「必要 / 期望 / 禁止」这一个轴，回答的是**业务后果**；没有一个轴回答**知识性质**。

复核侧现状：复核页只能高亮关键词（`static/highlight.js` 的 `rvMark`）。没写关键词的条目没有任何定位，包括清单型事实、需要 judge 的事实、全部禁止事实和前提，评审人只能通读整段回答。后期的复核导读和可解释判定，都要求模型给出的片段、判据结论能精确挂到某个条目上。所以条目本身要先具备稳定的锚点身份。

## 3. 条目性质

### 3.1 定义与判别

| 性质 | 判别依据 | 例 |
| --- | --- | --- |
| 客观（缺省） | 存在**可核验的唯一正确答案**：资料可查的规则、数值、清单成员、流程顺序 | kr-0203 F1「入货通知」；kr-0210 F1「对资料进行初步审核，防止报关或融资环节因信息错误产生风险」（规范总述原文） |
| 主观 | 合理答案不唯一：做法建议、最佳实践、取舍判断；回答给出其他合理做法时不算错 | 「报价单应注明付款方式」「建议提前与保险公司确认出单时间」 |

**判别时只看答案是否唯一，不看表述是否多样。** 上表第二个客观例子表述很开放，但规范里有原文，所以仍是客观。表述多样的问题已经由「不写关键词、交给 judge」处理（CASE-STRUCTURE §2.9），与性质无关。编写规则里要写明这一点，否则编写人会按「好不好写关键词」来打标。

### 3.2 与现有轴的关系

性质与「必要 / 期望 / 禁止」正交：

| | 客观 | 主观 |
| --- | --- | --- |
| 必要 F | 常见（规范要求） | 允许，check 提示「请确认不是期望事实」 |
| 期望 E | 允许 | 常见（技巧、最佳实践） |
| 禁止 X | 错误的事实（「未收尾款也可先电放」） | 应避免的做法（「建议报价单不写付款方式，留给谈判」） |

前提、路径、拒答**不带性质**：

- 前提判的是 agent 前一轮是否给出了某个回答，天然客观；
- 路径是机械判定；
- 拒答只有一个二元判断。

### 3.3 md 写法（样例实例）

```markdown
## 必要事实
- F1：FOB 报价不含海运费和目的港费用 【关键词：不含海运费】【证据：R1】

## 期望事实
- E1：报价单应注明付款方式及比例 【外部】【性质：主观】
- E2：报价单应注明报价有效期 【外部】【性质：主观】【部分判据：只写"短期有效"、未给具体期限算部分】

## 禁止事实
- X1：建议报价单不写付款方式，留到谈判时再定 【外部】【性质：主观】
```

规则：

- `【性质：客观】` 与不写等价；`【性质：主观】` 才有效果。
- `【部分判据：…】` 选填，**只允许出现在必要 / 期望的主观条目上**。客观条目的「部分」尺度是统一的（见 §4.2），不需要逐条补充；禁止条目的结论刻度只有「采信 / 未采信」，没有「部分」，写了报错。
- `【性质】` 接受 mapping 中对 必要 / 期望 / 禁止 三类事实的 `attrs` 声明；`【部分判据】` 只声明在必要 / 期望上。
- 属性值内不得出现「【」「】」（行尾属性按此定界，CASE-STRUCTURE §2.4）。`【部分判据】` 是长自由文本，最容易踩线；踩线时整段文字会被当作事实正文，check 按「正文含【」报错并提示这一限制。

### 3.4 编译产物（样例实例）

缺省值不落键：客观条目的编译行和现在逐字节一致。

```json
{"id": "E2", "kind": "expected", "text": "报价单应注明报价有效期",
 "turn": null, "group": null, "evidence": "external",
 "nature": "subjective",
 "partial_rule": "只写\"短期有效\"、未给具体期限算部分"}
```

### 3.5 check 规则

| 规则 | 级别 | 理由 |
| --- | --- | --- |
| 性质取值只能是「客观 / 主观」 | 错误 | — |
| 同一组内的成员性质必须一致 | 错误 | 组按「任一命中」计分，客观和主观的尺度不能混在一个计分单位里 |
| 必要事实标为主观 | 提示 | 缺了它业务上判错，与「合理答案不唯一」容易冲突，请编写人确认 |
| `【部分判据】` 写在客观条目上 | 错误 | 客观条目的部分尺度统一，见 §4.2 |
| `【部分判据】` 写在禁止条目上 | 错误 | 禁止的结论刻度只有「采信 / 未采信」，没有「部分」，该属性无语义 |
| 事实正文含「【」 | 错误 | 属性定界被破坏（长 `【部分判据】` 文本最易触发），报错时提示属性值内不得写「【」「】」 |
| 主观条目写了 `【关键词】` | 提示 | 主观条目合理表述不唯一，关键词命中容易漏判，P1 起主观条目的链不走 keyword |

### 3.6 指纹

| 指纹 | 是否计入 `nature` | 是否计入 `partial_rule` | 理由 |
| --- | --- | --- | --- |
| `standard_fp` | 是（仅主观时写键） | 是 | 改了判定尺度，必须产生新标准、重新判定 |
| `item_sha` | 是（仅主观时写键） | 是 | 人工改判是在某个尺度下做出的。客观条目「部分 = 不精确」，主观条目「部分 = 不充分」，尺度变了，旧的人工结论不再可信，应当作废 |
| `input_fp` | 否 | 否 | 与输入无关 |

「仅主观时写键」保证现有用例的 `standard_fp`、`item_sha` 不变：不需要迁移，不触发重判，现有人工改判全部保留。

> D1（已定，2026-10-28 评审采纳）：`item_sha` 计入性质，改性质时人工改判作废。理由见上表。另一种做法（不计入，复核页标「尺度已变更」）不采纳：改性质是低频操作，作废保证口径干净。

## 4. 判据表

判据是模型和人判断一个条目时**固定要看的几个角度**。用词上不叫「维度」，因为「维度」在本项目里指评测维度（知识召回等）。

### 4.1 定义

按 类型 × 性质 固定，以常量 `CRITERIA` 放在 `scoring/items.py`，与 `SCALES` 并列。它是判定契约的一部分，和 `SCALES` 一样随代码版本走，**不做成配置文件**：判据一改，判定的含义就变了，这不是使用者应该调的参数。

| 类型 × 性质 | C1 | C2 | C3 |
| --- | --- | --- | --- |
| 必要 / 期望 · 客观 | 值一致：关键值、对象、条件与条目一致 | 完整：条目要求的内容都覆盖到了 | 无误导：没有改变含义的限定、混淆或附加错误 |
| 必要 / 期望 · 主观 | 覆盖：回答提出了该做法或等价做法 | 充分：给出理由、适用条件或执行要点（有 `部分判据` 时以它为准） | 不相悖：没有给出与该做法相反的建议 |
| 禁止 · 客观 | 陈述：回答中出现了该错误内容 | 采信：作为结论或依据使用，而不是在纠正时复述 | — |
| 禁止 · 主观 | 提及：回答中出现了该做法 | 推荐：作为建议提出，而不是作为反例提及 | — |

判据结果只取三个值：`满足 / 不满足 / 无法判断`。

### 4.2 从判据推出结论

结论由判据结果**按规则推出**，不由模型自由给出。这一条是 P1 自洽校验的依据。P1 的模型算子与复核导读只产出判据结果与片段，结论一律由本节的推导函数得出；judge prompt 不得另行复述推导逻辑——防止契约与实现漂移。

| 类型 × 性质 | 推导（从上往下，命中即止） |
| --- | --- |
| 必要 / 期望 · 客观 | C1 不满足且回答给出了矛盾值 → 错；C1 不满足且未涉及 → 未提及；C2 或 C3 不满足 → 部分；全部满足 → 对 |
| 必要 / 期望 · 主观 | C3 不满足 → 错；C1 不满足 → 未提及；C2 不满足 → 部分；全部满足 → 对 |
| 禁止（两种性质） | C1、C2 都满足 → 采信；否则 → 未采信 |
| 任一判据为「无法判断」 | 结论记 undecided，送人工 |

客观条目第一行需要区分「给了矛盾值」和「没涉及」。所以客观 C1 的「不满足」带一个子标记 `contra: true/false`，见 §5.2 的样例。

### 4.3 判据版本

`CRITERIA` 有版本号，写作 `criteria@1`，并计入模型算子的版本。判据改动后，模型算子随之升版本，缓存失效；人工的判据级标记按 §5.4 判断是否有效。

## 5. 复核锚点

### 5.1 锚点身份

一条复核标记挂在下面四级锚点上。级别越低越具体，上级失效时下级一并失效。

| 级别 | 锚点 | 身份 | 已有 / 新增 |
| --- | --- | --- | --- |
| 条目 | 用例里的一条事实 / 前提 / 路径 / 拒答 | (`case_id`, `item_id`) + `item_sha` | 已有 |
| 回答 | 一次会话的回答 | `answer_id` + `answer_sha` | 已有 |
| 判据 | 条目在某判据版本下的一个角度 | `criterion_id`（C1–C3）+ `criteria_ver` | **新增** |
| 片段 | 回答中某一轮的一段原文 | (`turn`, `quote`)；`start` / `end` 由校验时计算 | **新增** |

规则：

- `item_id` 继续沿用 md 里的 F1、E2、X1、P1、`path#n`、`refusal`，不另造 ID。用例内唯一已由 check 保证。
- 片段以 `quote` 原文为准，`start` / `end` 是派生值。回答经 markdown 渲染后偏移会变，页面高亮按原文匹配，复用 `rvMark`。
- 跨变体时，同一用例的 `item_id` 相同、`item_sha` 相同（同一份事实）。所以标记可以按用例聚合，例如统计「E1 的 C2 在所有变体上被评审人推翻了几次」。

### 5.2 模型依据（rationale）的契约

模型算子（P1）和复核导读输出同一种结构。导读就是不带 `verdict` 的依据。

```json
{"item": "E2", "criteria_ver": "criteria@1",
 "spans": [{"id": "s1", "turn": 1, "quote": "报价有效期一般写 7 天"}],
 "criteria": [
   {"id": "C1", "result": "满足",   "refs": ["s1"]},
   {"id": "C2", "result": "不满足", "refs": ["s1"], "note": "给了天数，没说明到期后价格如何处理"},
   {"id": "C3", "result": "满足",   "refs": []}],
 "hint": "给了有效期，缺适用说明",
 "verdict": "部分"}
```

客观条目 C1 不满足时的写法：

```json
{"id": "C1", "result": "不满足", "contra": true, "refs": ["s2"]}
```

P1 的三道机械校验：

1. **引用核对**：`quote` 必须在 `turn` 那一轮的回答中逐字出现，否则这次判定记 error。
2. **自洽核对**：按 §4.2 从 `criteria` 推出结论，与 `verdict` 不一致时记 undecided。
3. **引用支撑**：结果为「满足」或 `contra: true` 的判据，`refs` 不得为空。

### 5.3 复核标记的分类

| 标记 | 锚点级别 | 谁产生 | 影响分数 | 存放（P1） |
| --- | --- | --- | --- | --- |
| 条目改判（现有） | 条目 × 回答 | 人 | 是 | `reviews`（不变） |
| 模型依据 | 条目 × 回答 × 判据 × 片段 | 模型算子 / 导读 | 否（结论另算） | `verdicts.rationale_json` |
| 判据不同意 | 判据 | 人 | 否 | `review_marks` |
| 定位有误 | 片段 | 人 | 否 | `review_marks` |
| 清单外错误 | 回答（`item_id` 为空） | 人 | 否 | `review_marks` |

**为什么 `review_marks` 要和 `reviews` 分开**：`reviews` 里的每一行都进入 `effective_final`、改变分数，这是它的语义。判据级、片段级的标记只用于流程优化和 judge 质量统计，不能有任何路径流入分数。把两者放在一张表里，就得在每个读 `reviews` 的地方加过滤，迟早会漏一处。分表之后，隔离是结构保证的，不用靠约定。

`review_marks` 的结构（P1 建表，本期只定契约）：

```sql
CREATE TABLE review_marks(
  mark_id     INTEGER PRIMARY KEY,
  answer_id   TEXT NOT NULL,  answer_sha TEXT NOT NULL,
  case_id     TEXT,           item_id    TEXT,  item_sha TEXT,  -- 清单外错误时为空
  criterion   TEXT,           criteria_ver TEXT,                -- 判据级标记时填
  turn        INTEGER,        quote      TEXT,                  -- 片段级标记时填
  mark        TEXT NOT NULL,  -- criterion_disagree / span_wrong / unclaimed_error
  note        TEXT,  reviewer TEXT,  at TEXT NOT NULL);
```

样例实例：

```json
{"answer_id": "a-0193", "answer_sha": "9c1e…", "case_id": "kr-0301", "item_id": "E2",
 "item_sha": "4b7a…", "criterion": "C2", "criteria_ver": "criteria@1",
 "mark": "criterion_disagree", "note": "回答第二段说了逾期需重新报价，C2 应为满足",
 "reviewer": "codfish"}
```

### 5.4 有效性

| 标记 | 有效条件 |
| --- | --- |
| 条目改判 | `item_sha`、`answer_sha` 与当前一致（现行规则不变） |
| 模型依据 | 跟随所属 verdict 的键（标准、链、条目、回答） |
| 判据不同意 | 条目改判的条件 + `criteria_ver` 与当前一致 |
| 定位有误 | `answer_sha` 一致，且 `quote` 仍能在该轮匹配到 |
| 清单外错误 | `answer_sha` 一致。与标准无关：标准变了，回答里的错误依然是错误 |

失效的标记不删除，在统计中排除，复核页可按需显示「历史标记」，做法与 doc/09 的作废清单一致。
