# 概要设计方案

版本：v1（2026-10-22），依据业务过程 v3.2（[01](01-业务过程总览.md)）与 CASE-STRUCTURE（2026-10-22 修订 1）。详细设计见 [06-详细设计方案.md](06-详细设计方案.md)。

## 1. 系统定位与组成

三个独立可执行单元 + 一组 P0 工具，以文件契约为唯一接口，任何两个单元之间不共享运行时状态：

```text
┌─────────────┐  dist/evalset-<ver>.jsonl   ┌─────────────┐  out/<run>/results.jsonl  ┌─────────────┐
│  md2case    │ ──────────────────────────► │   runner    │ ────────────────────────► │  scoring    │
│ 用例编译器   │  dist/evalset-<ver>.diff.md │ 评测执行器   │  out/<run>/run.json       │ 离线判定器   │
│ (Python)    │                             │ (TypeScript)│                           │ (Python)    │
└─────────────┘                             └──────┬──────┘                           └─────────────┘
       ▲  evalset/{cases,knowledge,mapping}       │ spawn 每轮一个进程                     ▲ 判定明细/聚合
       └────────────── 反馈回写（状态降级）◄────────┤                                               │
                                                  ▼                                               │
                                           ElineAI CLI（dsh 兼容）──► elineai.21eline.com          │
                                           tools/p0-*（P0 验证与盘点）                                │
                                           ◄────────────────────────────────────────────────────────┘
```

| 单元 | 语言/运行时 | 职责 | 来源 |
|---|---|---|---|
| md2case | Python 3.10+，零三方依赖（PyYAML 除外） | check / convert / build / render；knowledge 加载；自动 diff；注入 rev 联动降级 | 昨日 685 行版本扩展 |
| runner | TypeScript / Node ≥22.15（内置 zstd），vitest | 规划（筛选/预演/锚点/成本估算）、环境快照、skill 副本物化与注入、逐轮驱动、观测、装配、续跑、inspect | 昨日 skill-eval-runner 扩展 |
| scoring | Python 3.10+（serve 需可选依赖 FastAPI/Jinja2 等） | 机器算子链判定 + 人工改判覆盖 + 口径聚合；SQLite 评测库（题目/期望/答案/判定/改判/结论）为判定与人工数据的唯一事实来源；题目级统计、比较轴与锚点绊线、复核服务按题目组织 | [08](08-判定算子扩展方案.md) + [09](09-评测结果管理改造方案.md)（v2 → v3 两步） |
| tools/p0-* | Node 脚本 | P0-1 隔离验证（生成脚本，现场执行）、P0-2 盘点（解析既有日志目录消息） | 新建 |

## 2. 数据契约（三个单元的全部接口）

1. **编译行（dist JSONL，schema 2）**：字段与语义以 CASE-STRUCTURE §6 为准。执行器读取 `uid/dim/history/turns/injections` 五字段，规划器在 forced 下另读 `topic/path`；其余字段随行带出。
2. **EpisodeRecord（results.jsonl，schema 3）**：每段会话一行，含定位、环境（evalset_version、skills_sha256）、干预（forced_skills、injections_applied）、状态、逐轮（input/output/status/observations{skills,tools,tool_errors,usage,ask_user,model}）、汇总、`case`（编译行原样内嵌）、artifacts。相对昨日 schema 2 的变化：+case 内嵌、+ask_user/model 观测、+error 原因码、快照移至 run.json。
3. **run.json**：环境快照（evalset/runner_profile/eline_profile{method,sha256}/skills_mode/skills_base/agent/models_observed）、计数、跳过项、预演提示、锚点清单、估算 vs 实际。
4. **diff.md（build 产物）**：五类变更（新增/退役/因降级移出/内容修订/rev 变化），供版本对比视图对齐分母。

契约只增不改；改语义升 schema 号，旧 schema 拒绝续跑/拒绝混读。

## 3. 关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| 1 | md 是唯一数据源，自动降级直接改写用例 md 的 frontmatter（status + status_note） | CASE-STRUCTURE 原则 1；避免第二状态库 |
| 2 | 注入在编译期解析为 `{point,option,rev,file,key,value}`，运行期只做"复制基底 → 精确替换 → 计数 → overlay 接线" | 编译后执行器不再解析；替换计数是防"假 ec 题"的最后防线 |
| 3 | 环境快照是纯工具产物，不是门禁；唯一消费方是版本对比视图与 --resume 一致性检查 | 过程重量原则 |
| 4 | `skills_mode`（default-roots / isolated）是 Profile 中的一次性人工决策，isolated 以 P0 完成为前提；过渡期 ec 在规划期跳过 | 阻断项机制 |
| 5 | skills 副本物化对**所有会话**生效（isolated 模式），无注入即原样副本 | 环境对称原则 |
| 6 | 逐轮观测全部来自 session 日志解析（vendor 内核），探针不新增类型，ask_user 并入工具探针、model 并入用量探针（取 request/header） | 采集面收敛 |
| 7 | scoring 只读 results.jsonl；判定快照（judge 名/prompt sha/规则版本）由 scoring 自算写头部 | 单文件可分析 |
| 8 | 统计口径固定：通过率/前提成立率/归因比率 = 点估计 + Wilson 95% 区间；区间跨 0 不下方向性结论；锚点 trials ≥ 2 | 规模分级（< 50 用例）小规模档 |

## 4. 模块分解与依赖

```text
md2case.py
  parse（frontmatter/段落/属性【】）→ knowledge.load（yaml 注入点）→ check（结构/引用/--docs）
  → build（变体展开/注入解析/标签合并/随行带出/diff/rev 联动降级）
runner/src
  profile（新字段校验）→ planner（+环境检查/注入预演/锚点/成本估算/能力适配）
  → materialize（副本/替换/接线/留痕，isolated 时）→ episode-runner（沿昨日）
  → probes（vendor collector 修复 + ask_user/model）→ store（case 内嵌/快照/原因码/估算回写）
  → adapters（dsh-cli 沿昨日 + request/header 模型标识；web-ui 沿昨日）
scoring/（包，python -m scoring，结构见 08 §11 与 09 §9）
  items（拆条 §4.2 + 题目指纹 09 §4.1）→ operators/chain（算子链 + 判定缓存 §5）
  → store（SQLite 评测库：题目/期望/答案/判定/改判/结论，09 §6）
  → effective（人工改判覆盖 §6）→ policy（口径 §7 + 两点求值 09 §3）
  → views（能力/归因/质量/题目统计/比较轴/锚点绊线，09 §7）
  → cli（specs / score / rejudge / rescore / compare / export / backup / import-legacy / serve）
  → serve（复核服务：题目/题组/队列/比较/质量，从评测库取数分页）
tools/
  p0-1-verify.mjs（生成 overlay 副本 + 起 episode + 断言，现场执行）
  p0-2-inventory.mjs（解压既有 session 日志 → 提取 <available_skills> → 对照根目录 → skills-inventory.yaml）
```

依赖方向单向：scoring 不依赖 runner 代码；runner 不依赖 md2case；tools 依赖 runner 编译产物（lib/vendor）。

## 5. 执行模型与运行形态

- runner 为命令行工具（`run` / `inspect` 子命令），每段会话独立目录与进程树，并发 `--concurrency N`，退出码 0/1/2。
- 每轮一个 ElineAI CLI 进程，第二轮起 `--session-id` 续接；overlay 同时承担会话落盘重定向与（isolated 时）skill 根重定向。
- scoring 为离线批处理：`score`（单 run 判定+聚合）、`compare`（两 run 对比+绊线，读两个 run 目录）。
- CI 触发、报表平台不在本期（01 §1 范围表）。

## 6. 测试策略

| 层 | 方法 | 覆盖 |
|---|---|---|
| md2case 单测 | Python unittest，全量段落写法样例 + check 报错/提示清单逐条 | 四种输入写法、属性语法、注入引用、diff 五类、rev 降级、--docs |
| runner 单测 | vitest 纯函数 | profile 校验、快照计算、物化/替换/计数、预演、锚点合并、成本估算 |
| 编排测试 | 内存假适配器 | 多轮、失败停止、并发、续跑拒绝（快照五键）、run.json 内容 |
| 端到端 | 假 dsh（沿昨日 fake-dsh.mjs，扩展 skill-catalog 与 request/header 事件） | md → dist → results.jsonl → scoring 全链路；isolated/default-roots 两模式 |
| 回归 | 昨日真实 .work 日志（field-verify-eline） | vendor collector 修复后 skill 判定由"失败"转"成功"、模型标识提取 |
| 现场验证 | tools/p0-* | P0-1 隔离/forced/ask_user；P0-2 盘点 |

## 7. 工作包与里程碑

沿用可行性评估的 W1–W8 划分；关键路径 W2 → W3(P0-1) → W5(物化) → W8(smoke)。W4/W6/W7 可与 W5 并行。过渡期（P0 前）即可用 default-roots 模式跑 kr/mt 基线。
