# 评测集构建过程（链路 1）

版本：v3.2（2026-10-22）

## 1. 范围与原则

本篇定义从素材到 `dist/evalset-<ver>.jsonl` 的生产过程。用例的**结构**（frontmatter、段落、属性语法、字段语义）以 [CASE-STRUCTURE.md](CASE-STRUCTURE.md) 为唯一规范，本篇不重复，只讲**谁在什么阶段做什么、门禁卡在哪里**。

四条过程原则（对应 CASE-STRUCTURE 第 0 节设计原则）：

1. **md 是唯一数据源**——参考答案、证据、注入定义全部在 `cases/` 与 `knowledge/` 中维护，不另建数据库；文件系统就是评测集的存储形态。
2. **编译后执行器不再解析**——变体展开、注入引用解析都在 build 阶段完成，`dist/` 之后任何人不再碰 md 语义。
3. **knowledge 只定义"改什么"**——`key → value` 的物化属于执行期（见 [03](03-执行过程与注入.md)），生产线不修改任何 skill 文件。
4. **随行字段原样带出**——事实、证据、前提、参考答案编译时结构化带出，执行期不使用、不裁剪。

## 2. 资产与目录

```text
evalset/
  cases/<分组>/<id>.md      # 分组按业务域或批次自定，id 全局唯一且与文件名一致
  knowledge/<skill>.yaml    # 每个 skill 一个文件，登记该 skill 的注入点
  mapping.yaml              # 段落映射、改写枚举、标签词表——check 的依据
  dist/evalset-<ver>.jsonl  # 编译产物（不可变）
```

约束：

- **id 即文件名**：`<前缀>-<4 位数字>`，前缀对应维度（kr/mt/ec/sc/tc）；退役不复用。
- **一处知识，一个注入点**：同一段原文不登记成多个注入点；跨 skill 的知识各登记各的。
- `mapping.yaml` 是词表的唯一出处：标签不在词表中即 check 报错，改写类型不在枚举中即报错。

## 3. S1 编写与维护

作者工作流（产出 `draft` → `structured`）：

1. **立题**：确定维度与业务域。知识召回优先封闭题；多轮上下文 2–5 轮；错误知识纠正必须同时准备注入点与禁止事实。
2. **登记注入点**（ec 类先做）：在 `knowledge/<skill>.yaml` 找到被考的原文段，登记 id、file、key、选项。key 截取"能唯一表达这条知识"的长度——太短误伤，太长易因 skill 改版失效。
3. **写输入**：问题/对话/对话记录三选一；多轮用对话，注意第 N 轮更正类话术要在关键条件标明轮次与对象。
4. **写判定材料**：关键条件逐条列全；必要事实自包含（judge 看不到问题与对话）；每条事实标来源（【证据：Rn】或【外部】）。
5. **写变体**：只做同义改写与既定改写类型；对照关键条件做不泄露、不丢失限定词的自查（年份、数值、对象）。
6. 自检通过（S2 无报错）后把 status 置 `structured`。

批量生产可用生成器辅助：`render` 把结构化用例（YAML/JSON/JSONL）渲染成 md 交业务专家改写审阅；渲染即回读校验，漏段落当场报出，但不阻断写文件。

## 4. S2 check 校验

`check` 对源文件做全量静态校验，所有问题带行号一次报出。两级severity：

- **报错**（必须清零，否则 build 拒绝产出）：结构与枚举类（未定义段落、必填缺失、id/前缀/dim 不符、编号重复、属性非法、标签不在词表）、引用类（R/J/注入点/选项不存在、注入点选多选项）、维度特有类（ec 缺注入或禁止事实、非 ec 带注入）、一致性类（组唯一成员、组内轮次不一致、X 写关键词、证据与外部同现、【整段】轮数不符、轮次越界）、门槛类（reviewed 及以上缺参考答案或仍有未标注来源的事实）。
- **提示**（不阻断，但进入评审意见）：指代词残留、kr/ec 必要事实未标来源、变体泄露嫌疑（被替换轮缺本轮关键词或混入更早轮关键词）、相对日期。

**与文档一致性校验**（需要 `--docs` 指向 skill 根）：

- **报错**：注入点 key 在 file 中找不到；内联证据的原文在文档中找不到；**注入点 key 出现在 skill 的 frontmatter（name / description）中**——注入会同时改变路由目录，ec 混入路由变量。
- **提示**：注入点 key 在 file 中的**命中次数 ≠ 1**（替换语义是全匹配，多处命中可能误伤其他知识，需作者确认）。

这项在本地开发时跑，也在 CI 中对当前 skill 版本定期跑——skill 改版是注入点失效的主要来源。`--docs` 指向的是评测基底（Profile `skills_roots` 所列目录，见 [01](01-业务过程总览.md) 第 2 节 P0-2），而不只是用户 skill 根。执行期的规划阶段会对当时的基底再做一次同口径预演（见 [03](03-执行过程与注入.md) 第 3 节），因为 run 时的 skill 版本可能晚于最近一次 check。

## 5. S3 业务评审、S4 准入

评审人按 CASE-STRUCTURE 第 9 节编写规则逐条核两条判断标准：

- **问题充分**：换一个懂业务的人来答不会出现第二种合理理解；
- **事实必要**：业务专家看到缺这条的回答会判错；不必要就降为期望事实或移入备注。

评审通过的置 `reviewed`（此时参考答案必填、事实来源无未标注——check 已在门槛上保证）。S4 准入（置 `admitted`）一期不单独执行：build 默认收录 `structured,reviewed,admitted`，规模上来后再启用准入，由评测负责人确认注入点、路径约束与标签没有与既有用例冲突。

准入后原则上只允许两类改动：

- **typo 级笔误**：不改变语义，用例保持 `admitted`、不退役；但已发布的 dist 不可变，修正**随下一版 ver 一起重新 build**，自动 diff 中显示为"内容修订"。
- **实质性修改**：整条退役（`retired`）另立新 id。

避免"admitted 用例悄悄变语义"导致跨版本不可比。何为 typo 级由评测负责人判定，判定标准：改后关键条件、事实、注入、路径均不变。因为实质性修改必须换 id，所以同一 uid 内容有变的行在定义上就是 typo 级修订，工具据此分类，不需要人工标注。

**锚点用例**：评测负责人从 `reviewed` / `admitted` 用例中选定一组 uid，写入 `runner/anchors.txt`（一行一个，数量按 [01](01-业务过程总览.md) 第 9 节规模分级，覆盖各维度，不含诱导类变体）。**选取标准是稳定**：优先历史通过率高且稳定的用例（天然偏向 kr/mt）；ec 锚点的"通过"只在前提成立的有效会话上定义，注入生效率的波动不触发绊线。用于发现平台侧模型漂移与环境异常。锚点 uid 不在当前 dist 中时，规划器在 `--dry-run` 输出中提示，负责人替换即可，不需要另外记录。

## 6. S5 build 编译

```bash
python md2case.py build cases/ -o dist/evalset-<ver>.jsonl --version <ver>   # 默认 structured,reviewed,admitted
```

编译规则（CASE-STRUCTURE 第 5 节）在过程上的落点：

| 规则 | 过程含义 |
|---|---|
| 种子与每个变体各一行，uid = `<id>#n` | 判定与统计的最小单位在编译期就固定 |
| 输入统一展开为 `turns[]` | 四种多轮写法从此无差别 |
| `@注入点/选项` 解析为 `{point, option, rev, file, key, value}` | 执行器拿到的注入是"可直接物化"的操作，不再回查 knowledge |
| 证据 `@注入点` 解析为 `{doc, quote: key}` | 证据与注入共享同一锚点，知识改版时二者一起暴露 |
| 标签合并（用例自带 + 注入点继承，各标来源） | 业务标签的维护成本集中在注入点上 |
| 关键条件/前提/事实/路径/证据/参考答案结构化带出 | 执行期不读取、判定期直接用 |
| 有错不产出 | check 门禁在 build 内部再卡一次 |

产物 `dist/evalset-<ver>.jsonl` 不可变：发布后任何修改（含 typo 修订）都以新 ver 重新 build。ver 建议日期加序号（如 `v20261022-1`），run 清单的环境快照记录其 sha256。

**自动 diff**：build 时指定上一版（`--prev dist/evalset-<上一 ver>.jsonl`），md2case 对比两版 dist 与用例源的 status，生成 `dist/evalset-<ver>.diff.md`，按五类列出：

| 类别 | 判定方式 |
|---|---|
| 新增 | uid 只在新版 |
| 退役 | uid 只在旧版，且源文件 status 为 `retired` |
| 因降级移出 | uid 只在旧版，且源文件 status 为 `structured`（附 status_note 末条） |
| 内容修订 | uid 两版都在，编译行内容不同 |
| 注入 rev 变化 | uid 两版都在，injections 的 rev 不同 |

diff 文件是跨版本对比时对齐分母的输入，由 scoring 的版本对比视图直接读取。

## 7. knowledge 维护过程

注入点是**事实与 skill 原文的双重锚点**，维护规则（CASE-STRUCTURE 第 3 节）对应到日常过程：

1. **登记**：新增注入点（选项从无到有）随时可做，不影响已 admitted 用例。
2. **改值**：选项 value 修改必须升 rev；key 修改视同全部选项失效，同样触发联动。
3. **联动降级**：key 或 rev 变化 → 所有引用用例（`reviewed` 或 `admitted`）自动降回 `structured`，`status_note` 追加如 `收汇保单尾号/反转 rev 1→2，需复核`；用例重走 S3 评审，复核通过前不进入新版 dist。
4. **与 skill 改版对账**：定期（或 skill 发布时）跑 `check --docs`，key 找不到即说明 skill 已改版，先修 knowledge 再谈用例。
5. **退役**：注入点随知识下线可保留在 yaml 中不引用；不删除历史，保证旧 dist 与旧结果可解释。

## 8. 版本发布清单

以下由工具保证，不需要人工逐项确认：check 报错清零（build 内部再卡一次）、ver 递增与 dist 不可变（md2case 拒绝覆盖已存在的 ver）、五类 diff（自动生成）。

负责人只做两件事：

- [ ] 过目自动 diff（规模分级见 [01](01-业务过程总览.md) 第 9 节：小规模过目即可）；
- [ ] `check --docs` 中命中次数 ≠ 1 的提示，确认是有意为之还是 key 截得太短。
