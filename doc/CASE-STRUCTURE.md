# Agent 评测用例结构设计

版本：2026-10-22（修订 1：§2.10 路径语义、§2.11 证据文件路径、§6 读取字段表、§8 对应 check 规则，与过程文档 v3.1 对齐）

## 0. 范围

本文只定义**用例结构**：用例如何编写，以及如何编译成执行器可读取的结构化数据。

| 在范围内 | 不在范围内（由执行器或后续阶段负责） |
|---|---|
| 用例 md 的写法 | 会话的创建与续接、overlay、工作区 |
| 注入点与注入选项（knowledge） | 注入的执行：副本、替换、隔离 |
| 标签 | 日志的解析与留存 |
| 编译规则与编译产物 | 判定、打分、汇总 |
| check 校验规则 | 压缩、子 agent、失败与重试 |

适用场景：CLI（headless）、短对话、多轮对话（不涉及压缩）、基于 skill 的评测、动态注入。

设计原则：

1. **md 是唯一数据源。** 参考答案、证据、注入都写在用例或 knowledge 中，不另外维护数据。
2. **编译后执行器不再解析。** 变体展开、注入引用都在编译阶段解析完毕，执行器只读编译产物。
3. **注入只在运行时生效。** knowledge 只定义"改什么"，原始 skill 文件永远不会被评测改动。
4. **随行字段原样带出。** 事实、证据、参考答案等字段执行阶段不使用，编译时原样带出，供后续判定使用。

---

## 1. 文件组成

```text
evalset/
├── cases/**/<id>.md          # 用例，一个文件对应一个种子及其变体
├── knowledge/<skill>.yaml    # 注入点与注入选项
├── mapping.yaml              # 段落映射、枚举值、标签词表
└── dist/evalset-<ver>.jsonl  # 编译产物：一个变体占一行
```

## 2. 用例 md

### 2.1 整体结构

```markdown
---
<frontmatter>
---

## <段落标题>
<段落内容>
```

规则：

- 第一个 `##` 标题之前不能有正文。
- 出现未定义的二级标题，check 报错。
- 段落顺序不限，建议按 2.3 节的表格顺序书写。
- 槽位与值之间的冒号、文档与章节之间的斜杠，全角、半角都可以。
- `槽位：值` 一律以**第一个**冒号切分。

### 2.2 frontmatter

| 字段 | 必填 | 取值与含义 |
|---|---|---|
| id | 是 | `<前缀>-<4 位数字>`，前缀见第 7 节。全局唯一，与文件名一致；用例退役后不复用 |
| dim | 是 | 维度，见第 7 节，必须与前缀对应 |
| status | 是 | `draft` → `structured` → `reviewed` → `admitted` → `retired` |
| status_note | 否 | 状态变更的原因。人工填写；注入选项的 rev 变化时，也会自动追加 |
| answerable | 否 | 默认 `true`。知识库中没有答案的题写 `false` |
| history | 否 | `live`（默认）：逐轮发送。`prefill`：使用预置历史，当前执行器不支持，规划阶段会跳过 |
| topic | 否 | 业务域，与 profile 中 `routing` 的键使用同一套名称。不是 skill 名 |
| granularity | 否 | `环节`：问流程或清单。`细节`：问具体值 |
| pair | 否 | 镜像用例的 id，统计口径待定（见第 11 节） |
| tags | 否 | 场景、难点、来源三类标签，见第 4 节 |
| source | 否 | 素材来源，给人看 |
| owner | 否 | 负责人 |

### 2.3 段落

| 标题 | 编号前缀 | 何时必填 | 执行阶段是否使用 |
|---|---|---|---|
| 问题 / 对话 / 对话记录 | — | 三选一 | 是 |
| 关键条件 | — | 总是 | 否（供 check 与审阅使用） |
| 注入 | J | 错误知识纠正必填，其他维度不得出现 | 是 |
| 前提 | P | 可选 | 否（供判定使用） |
| 必要事实 | F | 总是 | 否 |
| 期望事实 | E | 可选 | 否 |
| 禁止事实 | X | 错误知识纠正必填 | 否 |
| 路径 | — | 可选 | 否 |
| 证据 | R | 可选 | 否 |
| 参考答案 | — | 进入 reviewed 前必填 | 否 |
| 变体 | V | 可选 | 是（编译时展开） |
| 备注 | — | 可选 | 否 |

编号只要求在本用例内唯一，各段落分别从 1 开始编号。删除一条后允许留下空号，不重排，避免与历史结果对不上。

### 2.4 属性语法

属性写在行尾，格式为 `【名称：值】`，多个值用 `、` 分隔。正文中不得出现 `【`。

| 属性 | 适用段落 | 含义 |
|---|---|---|
| 关键词 | 关键条件、必要事实、期望事实 | 关键条件中用于变体泄露检查；事实中用于规则判定 |
| 轮次 | 关键条件、前提、事实、路径、变体 | 第 N 轮，N 按用户消息计数 |
| 对象 | 关键条件 | 同一段对话中有多笔业务时，用 A、B…… 区分 |
| 组 | 必要事实 | 同组事实满足其一即可，同组事实的轮次必须相同 |
| 证据 | 事实 | 引用 R 编号 |
| 外部 | 事实 | 资料外事实，不能与【证据】同时出现 |
| 注入 | 前提 | 引用 J 编号 |
| 改写 | 变体 | 改写类型，枚举值见 mapping.yaml |
| 整段 | 变体 | 替换整段对话 |

### 2.5 输入：问题 / 对话 / 对话记录

三种段落只能写一种。

**问题**：单轮输入，一段文字。

**对话**：多轮输入，有三种写法。

```markdown
## 对话
- 第 1 轮用户消息
- 第 2 轮用户消息
```

```markdown
## 对话
### 第 1 轮
用户消息，可以多行
助手：参考回复（可选）
### 第 2 轮
用户消息
```

````markdown
## 对话
```jsonl
{"role": "user", "content": "……"}
{"role": "assistant", "content": "……"}
```
````

**对话记录**：以 `用户：`、`助手：`（或 `User:`、`Assistant:`）开头的行开始一条新消息，其余行接续上一条。

共同规则：

- 必须以用户消息开始，每条用户消息算一轮。
- 多轮对话为 2 到 5 轮。
- 写在对话中的助手消息只作参考，`live` 模式下不发送。

### 2.6 关键条件

```markdown
## 关键条件
- 出运时间：2025 年 10 月 【对象：A】【轮次：1】【关键词：10 月、十月】
```

列出使问题充分的每一个条件，用于审阅和变体检查。三个属性都是可选的。写了【轮次】和【关键词】的条件，check 会据此做变体泄露检查（第 8 节）。

### 2.7 注入

```markdown
## 注入
- J1：@收汇保单尾号/反转
```

写法为 `@注入点/选项`，引用 knowledge 中的定义（第 3 节）。规则：

- 同一个注入点只能选一个选项。
- 一条用例可以引用多个注入点。

### 2.8 前提

```markdown
## 前提
- P1：2025 年 10 月出运的这单，保单号后三位填 500 【轮次：1】【注入：J1】
```

前提声明的是后续用户台词所依赖的 agent 回答。例如第 2 轮用户说"你引用的规则写反了"，就预设了 agent 第 1 轮答的是 500。

前提在执行阶段不判断，也不中断执行；判定阶段如果发现前提不成立，该 episode 记为无效，不计为答错。前提文本必须自包含。

### 2.9 事实

```markdown
## 必要事实
- F1：内容 【关键词：甲、乙】【轮次：2】【组：G1】【证据：R1】

## 期望事实
- E1：内容 【轮次：2】【外部】

## 禁止事实
- X1：内容 【轮次：2】【证据：R1】
```

| 类别 | 含义 |
|---|---|
| 必要事实 F | 缺了这条，业务上就判错 |
| 期望事实 E | 缺了不算错，但值得统计 |
| 禁止事实 X | 回答中不得采信 |

规则：

- 事实文本必须自包含：只看这条事实和回答就能判定，不得出现"前文""上述""第 N 轮"这类指代。
- 禁止事实不写关键词。agent 纠错时往往会复述错误值，关键词匹配会把纠错误判为采信。
- 清单型事实、数值有歧义的事实不写关键词，交给 judge 判。
- 不写轮次时，判最后一轮。
- 每条事实的来源有三种状态：`【证据：Rn】` 表示资料内；`【外部】` 表示资料外；两者都不写表示未标注。进入 reviewed 之前，未标注的必须全部消除。

### 2.10 路径

```markdown
## 路径
- 必须：加载 skill trade-company 【轮次：1】
- 禁止：加载 skill trade-documents
```

- 第一期只支持 `必须` 和 `禁止` 两种约束，动作只支持 `加载 skill <名称>`。
- 「必须」写【轮次：N】时，指截至第 N 轮（含）会话中已加载过；不写轮次时，指截至最后一轮已加载过。skill 加载后内容留在上下文中，不要求在该轮重新加载。
- 「禁止」写【轮次：N】时，指第 N 轮发生加载即违反；不写轮次时，指整个会话中任何一轮加载即违反。
- forced 会话不判定路径约束。

### 2.11 证据

```markdown
## 证据
- R1：@收汇保单尾号
- R2：trade-company:trade-company.md / 4.6 资方与服务主体对应关系 ｜ 原文：| 海发 | 青岛海发商业保理有限公司 | 青岛易汇智供应链管理有限公司 |
```

有两种写法：

- **引用注入点**：`@注入点`，原文就是该注入点的 key。
- **内联**：`<文档> / <章节>`，可以再加 ` ｜ 原文：<原文>`。

规则：

- 文档写作 `skill 名:相对路径`，路径相对 skill 根书写（平铺形态如 `trade-company:trade-company.md`，目录形态如 `trade-company:trade-company/SKILL.md`），**必须显式写出**，不设默认值。
- 原文分隔符只能用全角 `｜`，因为原文中常带有半角 `|`。
- 先按 ` ｜ 原文：` 切出原文，再对前半部分按第一个 ` / ` 切分文档和章节。

### 2.12 参考答案

参考答案是一段完整的标准回答，不参与打分，只用于审阅和作为 judge 的参照。参考答案中不得出现必要事实、期望事实以外的结论。

### 2.13 变体

```markdown
## 变体
- V1：替换后的用户消息 【轮次：2】【改写：口语】
- V2：替换后的用户消息 【改写：极简】
- V3：【整段】【改写：语序】
  - 第 1 轮用户消息
  - 第 2 轮用户消息
```

| 写法 | 替换范围 |
|---|---|
| 带【轮次：N】 | 只替换第 N 条用户消息 |
| 不写轮次 | 替换最后一条用户消息 |
| 【整段】 | 替换全部用户消息，轮数与种子一致，各轮所属的对象也必须与种子一致 |

`诱导` 类改写会在问题中预设答案，不计入同义一致性的统计。

### 2.14 备注

一段文字，写给审阅人看，不参与评测。

## 3. 注入点与注入选项（knowledge）

```yaml
# knowledge/trade-company.yaml
- id: 收汇保单尾号
  file: trade-company/SKILL.md
  key: 之前出运业务保单号后三位为 400，之后为 500
  tags: [业务/收汇]
  options:
    反转: {value: 之前出运业务保单号后三位为 500，之后为 400, rev: 1}
    删除: {value: "", rev: 1}
```

| 字段 | 含义 |
|---|---|
| id | 注入点名称，全局唯一 |
| file | 相对 skill 根目录的文件路径 |
| key | 被替换的原文，同时作为证据锚点 |
| tags | 业务类标签，被引用它的用例继承 |
| options | 注入选项：选项名 → value + rev。value 为空表示删除 |

注入语义：

- 只支持 key → value 的精确字符串替换：不用正则，不忽略空白，替换文件中所有匹配位置。
- 注入只作用于单个 episode 的 skill 副本，原始 skill 只读。
- key 要截取能唯一表达这条知识的那一段：太短容易误伤其他内容，太长容易因为 skill 改版而失效。

维护规则：

- 选项只允许新增，不允许改名。
- 选项的 value 一旦修改，rev 必须加 1。
- key 或某个选项的 rev 发生变化时，所有引用它的用例自动降回 `structured`，并在 status_note 中追加记录，例如 `收汇保单尾号/反转 rev 1→2，需复核`。

## 4. 标签

```yaml
# mapping.yaml（节选）
tags:
  业务: [收汇, 资方对应, 退税, 单证, 合同]
  场景: [用户更正, 多对象, 跨 skill]
  难点: [规则反转, 清单完整, 数值推算]
  来源: [人工构造, 生成, 现场记录]
```

- 标签格式为 `命名空间/值`，必须取自词表，check 会校验。
- 用例只写 `场景/`、`难点/`、`来源/` 三类；`业务/` 类在编译时从引用的注入点继承。
- 标签只用于检索和分组，不参与打分。

## 5. 编译规则

| # | 规则 |
|---|---|
| 1 | 每个种子和每个变体各编译为一行；种子的 uid 为 `<id>#0`，变体 `Vn` 的 uid 为 `<id>#n` |
| 2 | 输入统一展开为 `turns[]`，元素为 `{role, content}`；变体按 2.13 节的规则替换用户消息 |
| 3 | `@注入点/选项` 解析为具体操作，记录 point、option、rev、file、key、value |
| 4 | `@注入点` 形式的证据，解析为 `{doc, section: null, quote: key}`，doc 的文件路径取该注入点的 `file` |
| 5 | 标签合并：用例自带的标签，加上从注入点继承的标签，并标明每个标签的来源 |
| 6 | 关键条件、前提、事实、路径、证据、参考答案、备注，结构化后原样带出 |
| 7 | build 只收 `admitted` 状态的用例（可以用参数放宽）；任何文件有错误就不产出 |

## 7. 维度与前缀

| dim | 前缀 | 额外要求 |
|---|---|---|
| 知识召回 | kr | 优先出答案短而明确的封闭题，考查内部知识 |
| 多轮上下文召回 | mt | 使用对话或对话记录，2 到 5 轮 |
| 错误知识纠正 | ec | 必须写注入和禁止事实 |
| 同义请求一致性 | sc | 保留还是改为统计指标，待定（见第 11 节） |
| 工具调用 | tc | 第一期不做，前缀保留 |

## 8. check 校验

**报错**（build 不产出）：

- 未定义的段落；必填段落缺失；输入段落不是恰好一个。
- 前缀与 dim 不对应；id 与文件名不一致；id 重复。
- 段落内编号重复；属性名不合法；属性出现在不适用的段落。
- 引用的 R、J 编号不存在；`@注入点` 或选项在 knowledge 中不存在；内联证据的文档未写相对路径。
- 同一个注入点被选了多个选项；非 ec 用例写了注入；ec 用例缺少注入或禁止事实。
- 注入点的 key 在 file 中找不到（需要 `--docs`）；内联证据的原文在文档中找不到（需要 `--docs`）。
- 组只有一个成员，或组内事实的轮次不一致；禁止事实写了关键词；【证据】与【外部】同时出现。
- 标签不在词表中。
- 【整段】变体与种子轮数不一致；【轮次】超出对话轮数。
- reviewed 及以上状态缺少参考答案，或仍有未标注来源的事实。

**提示**（不阻断）：

- 事实或前提中出现指代词（前文、上述、第 N 轮、按……作答）。
- 知识召回或错误知识纠正的必要事实未标注来源。
- 变体泄露：被替换的那一轮缺少本轮条件的关键词，或者包含了更早轮次条件的关键词。
- 问题或变体中出现相对日期（去年、上个月、下周等）。

---

## 9. 编写规则

1. **问题要充分**：换一个懂业务的人来答，不会出现第二种合理理解。
2. **事实要必要**：缺了这条，业务专家会判错；否则移到期望事实或备注。
3. **事实要自包含**：judge 看不到问题和对话。
4. **变体不得泄露被考的上下文**，也不得丢失决定答案的限定词，例如年份。
5. **不写相对日期**，一律写绝对日期。
6. **多轮更正**：在关键条件中写明哪一轮更正、以哪个值为准；被更正掉的旧值写成禁止事实。
7. **数值关键词只写一种规范形式**，例如 `9000`，格式差异由判定层归一化。
8. **一处知识，一个注入点**：同一段原文不要登记成多个注入点。
