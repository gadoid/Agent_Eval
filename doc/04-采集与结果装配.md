# 采集与结果装配（链路 4）

版本：v3.2（2026-10-22）

## 1. 范围

定义执行期的信号采集、结果装配与判定交付。目标只有一个：**`results.jsonl` 单文件即可分析**——判定、聚合、复核都不需要再回头读评测集源文件或 md。

采集发生在 S7 每一轮（探针），装配发生在 S8 收尾（store）。

## 2. 逐轮观测（EpisodeRecord.turns[]）

每轮固定记录：

| 分组 | 字段 | 来源 |
|---|---|---|
| 定位 | index、source（live/prefill） | 执行器 |
| 输入 | input（实际发送文本，含 forced 注入的 `/skill名`） | 驱动器/干预 |
| 输出 | output（本轮回答全文） | session 日志 |
| 运行 | status、turn_end、exit_code、duration_ms | 执行器 |
| 观测 | observations：skills、tools、tool_errors、usage、ask_user（次数与是否自动放行）、model（日志可得时，否则 null） | 四类探针 |

口径要点：

- `status` 只表示**运行是否正常**（ok/incomplete/timeout/error），不表示答对。
- 每轮的 observations 只含本轮新增事件（日志按轮切分），多轮题的 `usage` 逐轮独立可加总。
- `observations.skills` 逐轮记录，是判定「路径」约束（必须/禁止加载 skill，含轮次语义）的直接素材。

## 3. 会话装配（results.jsonl，每段会话一行）

EpisodeRecord 分组字段：

| 分组 | 字段 | 说明 |
|---|---|---|
| 定位 | schema、run_id、episode_id（`uid\|干预\|trial`）、uid、case_id、variant_index、dim、topic、granularity、mode、trial、history | uid 主键，跨版本可追溯 |
| 环境 | evalset_version、skills_sha256（本会话副本，注入后） | 完整环境快照只在 run.json 中一份（见第 4 节），不在每行重复 |
| 干预 | forced_skills、injections_applied（point/option/rev/found） | 注入物化结果留痕，key 未命中在此可见 |
| 状态 | status（全部轮 ok 为 ok）、error、failed_turn | 运行状态，非判定 |
| 逐轮 | turns[]（见第 2 节） | |
| 汇总 | final_output（最后一轮回答，默认打分对象）、loaded_skills、usage、duration_ms | |
| **随行** | `case`：编译行原样内嵌（conditions、preconditions、facts、path、evidence、tags、reference_answer…） | CASE-STRUCTURE「随行字段原样带出」的落点；执行期不读，判定直接用 |
| 产物 | artifacts：session_log（日志文件路径）、session_id、run_dir | 复盘入口 |

关键设计：**随行字段内嵌**。昨日 scoring 需要同时读 evalset.jsonl 与 results.jsonl 做 join；本设计把编译行整体塞进 `case` 字段，判定输入只剩一个文件。评测集版本与 run 的对应关系由每行的 `evalset_version` 保证，不存在错配。

## 4. 运行清单（run.json）

run 结束写入：run_id、起止时间、**环境快照** `snapshot`（键见 [01](01-业务过程总览.md) 第 5 节，judge 一项除外）、Profile 全文、执行器名称/版本/能力、干预方式、trials、并发数、会话计数（计划/续跑跳过/本次执行）、各状态计数与错误占比、被跳过的用例及原因（prefill 不支持、隔离未验证、routing 缺失、forced 目标被禁止、注入点文件缺失、注入预演未命中…）、注入预演中 found > 1 的清单、本次纳入的锚点 uid、ask_user 自动放行语义（返回给 agent 的内容）。

以下情况由 store 自动在 run.json 中告警，不阻断：`models_observed` 出现多个值（`model_drift: true`，结论需按模型分组看）；isolated 模式下无注入会话的 `skills_sha256` 与快照 `skills_base` 不一致；规划时提示了 inventory 过期。

错误按原因码分列计数，`rate-limited`（平台限流）单独一列；同时写入 dry-run 的估算值与实际总 token、实际耗时，供下一次 run 的估算使用。

环境快照全部由工具计算，没有任何字段需要人工填写。

run.json 是第 4 道门禁的依据：错误占比超阈值时 run 标记不可采信，先排查环境再谈结论。

## 5. 产物留存与安全

```text
out/<run>/
  results.jsonl     判定与聚合的唯一输入
  run.json          运行清单
  verdicts.jsonl    逐条机器判定（python -m scoring score 产出）
  review.jsonl      人工改判（复核服务追加，只追加不改写，见 08 §8.2）
  scoring.json      判定与聚合输出（头部含判定配置摘要，见第 6 节）
  .work/<episode>/
    skills/         skill 副本（所有会话都有；有注入时为替换后版本，可复现该会话的知识状态）
    overlay.patch.yml
    session/        ElineAI 原生 session 日志——含业务数据与真实对话，注意存放与传输
    workspace/      会话结束即删（--keep-workspace 保留排查）
```

- session 日志是敏感产物：归档策略（保留时长、脱敏、存放位置）在 run 计划确认时一并明确。
- `.work` 目录在 run 结束后默认保留（注入副本与日志是结果的可解释性依据），workspace 自动清理。
- `inspect` 子命令可随时重放任一 episode 的日志事件，用于复核 7.3 类信号（skill 加载、工具调用）。

## 6. 判定交付（S9 的输入契约）

scoring 只读 `results.jsonl`，逐段会话判定、按 uid 聚合。判定项与随行字段的对应：

| 判定项 | 依据字段 | 口径 |
|---|---|---|
| 必要事实 F | case.facts（kind=required）+ 对应轮 output | 四级判定（对/部分/错/未提及）；有关键词先规则判，否定语境不认，其余交 judge；规则判"对"的条目进入复核（数值关键词可能出现在无关语境），复核比例按 [01](01-业务过程总览.md) 第 9 节：先全复核校准，一致率稳定后转抽样；规则判定版本变化时重新进入校准 |
| 期望事实 E | case.facts（kind=expected） | 缺了不算错，单独统计 |
| 禁止事实 X | case.facts（kind=forbidden） | 回答采信即错；纠错时的复述不算采信（judge 判，不做关键词匹配） |
| 前提有效性 | case.preconditions + 对应轮 output | 前提不成立 → 该 episode 记**无效**，不计为答错；前提成立率按 dim × mode 与通过率并列上报（见下文 6.1） |
| 路径约束 | case.path + turns[].observations.skills | 见下文 6.2 |
| 不可回答题 | case.answerable=false | 期望拒答/声明无据，走拒答判定 |
| 反问 | turns[].observations.ask_user | 不单独计分；事实判定结果按"直接作答 / 反问后作答"分组统计，避免自动放行掩盖问题不充分 |
| 同义一致性 | 按 case_id 跨 uid 配对（含变体） | 诱导类改写（variant.rewrite）排除在外 |
| 注入有效性 | injections_applied | found=0 的会话不进入 ec 判定，只进错误统计；found>1 的会话正常判定，在用例质量视图中列出 |

**判定配置摘要**（[08](08-判定算子扩展方案.md) §8.3，取代原 judge 快照）：scoring 在 scoring.json 头部自动写入 `judgment_snapshot`——算子清单（id@版本）、operators.yaml 与 policy.yaml 的 sha256、人工改判生效/作废数、未决排除数，由 scoring 自行计算，不由调用方传入。机器判定改为可插拔算子链（operators.yaml 配置），人工改判作为覆盖层经唯一合成函数 `effective_final` 参与；原 judge 函数注入接口已废弃，判定契约见 08 §4–§8。

### 6.1 前提有效性与 ec 主口径

live 模式下，ec 用例后续轮的台词预设了 agent 前一轮的回答（如"你引用的规则写反了"）。agent 没加载 skill、按常识作答或反问时，前提即不成立，会话记无效。无效集中出现在 natural 模式，会让 natural 的 ec 有效样本偏少且偏向"恰好加载了 skill"的会话。因此 prefill 落地前：

| 指标 | 口径 | 含义 |
|---|---|---|
| **ec 主口径：forced 通过率** | 前提成立的 forced 会话中，F 全对且 X 未采信的比例 | 纠错能力本身——skill 已保证加载 |
| forced 前提成立率 | 成立会话 / 运行 ok 的 forced 会话 | **注入生效率**：注入的错误知识被加载并主导了首轮回答的比率。偏低说明 agent 首轮没采用注入内容（被常识或其他 skill 覆盖），ec 用例本身需要复查 |
| natural 通过率 | 全部运行 ok 的 natural 会话中，前提成立且通过的比例（前提不成立计为未通过） | "路由 + 纠错"复合指标，不单独解读为纠错能力 |
| natural 前提成立率 | 同上，natural | 主要反映首轮路由，计入路由统计（6.3） |

其他维度前提成立率同样与通过率并列上报，口径同上。

### 6.2 路径约束语义

以 CASE-STRUCTURE §2.10 为准，下表为判定实现时的对照：

| 情形 | 口径 |
|---|---|
| forced 会话 | 路径约束**不判定**（记 `n/a`）：目标 skill 已经以命令方式注入，`必须` 恒满足无意义；`禁止` 与 routing 的冲突已在规划期跳过 |
| `必须：加载 skill X 【轮次：N】` | 截至第 N 轮（含）会话中**已加载过** X 即满足——skill 内容加载后留在上下文中，不要求第 N 轮重新加载 |
| `必须` 未写轮次 | 截至最后一轮已加载过 X |
| `禁止：加载 skill X 【轮次：N】` | 第 N 轮发生了 X 的加载即违反 |
| `禁止` 未写轮次 | 整个会话中任何一轮加载过 X 即违反 |

### 6.3 归因（natural 三分）

natural 会话中，一条 F 判错时按该会话截至判定轮的加载信号分三类：

| 类别 | 条件 | 归因与动作 |
|---|---|---|
| 未加载 | 未加载目标 skill，也未加载其他 skill | 路由失败 → 改 skill 描述 |
| 误加载 | 加载了其他 skill，未加载目标 skill | 路由误选 → 检查描述之间的区分度；**误加载集中在某一个 topic 上时，先查该 topic 的 routing 配置**——目标 skill 取自 routing 时，routing 配错会被这一类继承 |
| 加载但答错 | 已加载目标 skill | 知识或理解问题 → 看 forced 同 uid 的表现作参照 |

"目标 skill"取路径 `必须` 中的 skill；用例无路径时取 topic 经 routing 映射的 skill。

forced 结果只用作"该知识在 skill 中是否可用"的参照，不作为严格对照（两种模式下 skill 内容在上下文中的位置不同，见 03 第 5.1 节）。有 trials 时，比较的是各类别**比率**与 forced/natural **通过率之差**，不做单次结果配对。

### 6.4 统计口径

按 [01](01-业务过程总览.md) 第 9 节规模分级：

- **小规模（当前）**：通过率、前提成立率、各归因比率只报点估计 + Wilson 区间；版本对比给出差值及其区间，区间跨 0 时不下"变好/变差"的结论。
- **大规模**：再加 pass@k（k 次中至少一次通过，看能力上限）与 pass^k（k 次全部通过，看稳定性）。
- 聚合维度：dim × topic × mode；锚点只用于第 7 节的绊线，不并入能力视图的聚合。

## 7. 分析出口（S10）

判定明细之上，标准分析出口五类（对应总览第 8 节闭环；第 5 类锚点绊线只是对锚点 uid 的检查，不是新环节）：

1. **能力视图**：按维度/主题/mode 的通过率（带区间）与前提成立率，headline 取各维度主口径（01 第 8 节，ec 为 forced）；附"直接作答 / 反问后作答"分组；
2. **归因视图**：natural 三分归因（未加载 / 误加载 / 加载但答错）的比率，配 forced 同 uid 通过率作参照；
3. **用例质量视图**：judge 与人工复核不一致清单（→ 降级回写）、变体泄露嫌疑清单（→ 修用例）、规则判定复核不一致清单与一致率（决定是否转抽样）、注入 found>1 清单、forced 前提成立率偏低的 ec 用例；
4. **版本对比视图**：两次 run 按 uid 配对的通过率差异（带区间）。视图顶部自动打印两次 run 的**环境快照差异键**（含判定快照）；差异键多于被比较项时，结论需注明。分母按 md2case 自动 diff 中"因降级移出"对齐；
5. **锚点绊线**：同一锚点 uid 在上一次全量 run 中全部 trial 通过、本次全部 trial 失败时标红（锚点 trials 固定 ≥ 2，见 03 第 3 节；两次 run 的 `skills_mode` 不同时不比较），叠加两次 run 的 models_observed 与快照差异键。标红只表示"去看一眼"，不作统计结论；没有已知变更却出现标红时，按平台模型漂移、服务端状态串扰、环境异常的顺序排查。

五类出口由 scoring 包（views.py）实现，并在复核服务（`python -m scoring serve`，08 §9）中交互呈现——逐条对照期望改判、口径重算、多 run 对比与导出；report.mjs 仍可生成只读对话记录（不再扩展），但不是这些出口的主要呈现。
