# 组件评测扩展方案

版本：v1.0（2026-10-30 定稿）· 代码基线：`feat/eval-gaps` f1ed3ef + 计分逻辑版本提交（§7，定稿时一并推送）· 状态：定稿，按 §12 分期实施

本文回答一个问题：**现有实现怎样扩展，才能支撑模型、Skill、提示词、工具使用、Harness 的初期组件评测。**

全部改动落在现有文件内，不新增模块。

---

## 0. 已定事项

| # | 决定 |
| --- | --- |
| 1 | 评测对象按**能力**划分，不按插件划分。判断标准是：这项能力会不会改变模型看到的内容，或者模型能做的事。同一个插件可能既向模型暴露 tool，又渲染 UI |
| 2 | 集成进 Agent 的代码（结构化渲染、hook、UI、落盘）和 tool 实现的正确性，归**自动化测试**，不进 Agent_Eval。Agent_Eval 只记录它们的身份，保证集成代码变化不会悄悄混进评测结果 |
| 3 | 改变模型输入的集成代码（persona、检索注入、记忆等）：自身逻辑对不对靠测试；它对答案的影响作为**配置因子**，在评测中对比 |
| 4 | 模型可调用的 tools，评测的是**模型怎么用**（是否调用、调用时机），不评测 tool 本身 |
| 5 | 不新增模块，改动落在现有文件（§10）。header 观测归现有观测层 `runner/src/probes/index.ts`（它已在做 trace→Observations 并从 header 取模型），适配器对同一段日志文本调用——vendor/ 按同步规则不做业务修改（`runner/src/vendor/UPSTREAM.md`） |
| 6 | 现有数据都是测试数据：被测指纹字段变化后，评测库（demo 与 archive）**一次性重建**，不写迁移（沿用 doc/17 决定 10；schema 升级沿用决定 15 模式：旧 schema 库直接拒绝打开）。旧 results.jsonl 没有 header 观测，重导后工具观测列为 NULL，tools 轴只对新 run 生效（遇 NULL 拦截并提示，见 §3）。**schema v10 的全部列在 P1 一次建好**（§12），避免 P2 再升版本、再重建一次库 |

## 2. 被测配置身份

### 2.1 配置侧：subject 字段表（doc/15 §3.1）

| 字段 | 现状 | 改为 | 来源 |
| --- | --- | --- | --- |
| `eline_profile_sha` | 三个 cordis 文件（cordis.patch.yml、cordis.yml、package.json）的整体哈希 | **移出 subject**，保留在 snapshot | — |
| `persona_sha` | — | persona 类条目 config 的规范化哈希 | 合成后的条目按 **`id` 匹配**（`prompt_plugins` 按 id 声明、缺省 `['persona']`，§9-1） |
| `plugins_sha` | — | 其余条目（id + name + config）+ package.json 的 **`dsh.profile.bundles` 清单**；排除 persona 类与 agent-default-model | cordis.yml、cordis.patch.yml、package.json |
| `model` | profile 或 CLI 覆盖值，未覆盖为 null | **有效模型**：覆盖值，否则取合成后 `agent-default-model` 条目的 `config.model` | 同上 |
| `reasoning_effort` | 同上 | 同理，取 `config.reasoningEffort` | 同上 |
| `model_provider` | 同上 | 同理，取 `config.provider` | 同上 |

- 续跑一致性检查不受影响：`RESUME_KEYS` 比对的是 snapshot 里 `eline_profile` 整段（method/sha256/files），与 subject 是否含该字段无关。
- 合成顺序：package.json `dsh.profile.bundles` → cordis.yml → cordis.patch.yml → 运行期 overlay（不进指纹）；条目按 `- id:` 覆盖、`- insert:` 插入（DSH 现行规则，demo 的 cordis.yml 为空数组、persona 恰在 patch 层）。
- **bundle 盲区（插件与模型都适用）**：bundle 内部件（dsh-base/dsh-headless 提供的条目、版本，乃至默认模型与 persona）不在三件套本地内容里，本地合成拿不到。分字段兜底：
  - 插件层：§2.2 的 tools_sha 观测——生效工具清单变了必然体现在观测上；
  - 模型层：配置侧取不到时 subject 值**保持 null**（不猜），对比轴回退观测值（model 轴现行就回退 `models_json`，`request/header` 的 config 里 provider/model/reasoningEffort 已在采集）；run 启动时对「patch 没写 `agent-default-model`、也没有 CLI 覆盖」给提示，check 同；
  - **persona 层：没有可用的观测值**——`system_prompt_sha` 的文本含模型名和工作目录（§2.2 自己写了不能当身份），不能回退。persona 取不到配置时 `persona_sha` 保持 null，**persona 轴不可用**（null 不构成可对比的轴值，§3 拦截），run 启动给提示。
- cordis 解析**只在 runner（TS）一份**：snapshot 计算时解析，把 persona_sha、plugins_sha、有效 model/effort/provider 写入 snapshot 新段；Python 侧 `subject_of_manifest` 只读 snapshot 段（与「种子题规则只留一份」同思路）。字段表本身仍是双实现，`tests/fixtures/subject_manifest.json` 补字段，对拍测试照旧。
- 旧 manifest（无新字段）按缺省补 null，不写 unknown；配合决定 6 一次性重建，同一套配置的旧记录不会因缺字段分裂。
- 修好的两个方向：同有效模型（CLI 覆盖 vs cordis 缺省同值）→ 同一 subject_fp，不再假分裂；换 cordis 模型 → `model` 字段变化，不再靠整段哈希隐式承载。

### 2.2 观测侧：每段会话（不进 subject_fp）

已在 forced-episode fixture 中核实：会话日志的 `request/header` 带生效工具清单，`system/message` 带生效系统提示；**`request/header` 每会话一帧**，只出现在第 1 轮切出的日志里。

| 观测 | 来源 | 用途 |
| --- | --- | --- |
| `tools_sha` | `request/header.tools` 的 (name, description, parameters) 排序后哈希 | 工具对比轴（§3）；同 run 跨 episode 不一致时告警 |
| `tools_list` | 同上，只取名称 | 复核页展示；check 校验「调用 tool」的名称（§4.1） |
| `system_prompt_sha` | `system/message` 文本哈希 | **只做一致性观测**：文本里含模型名和工作目录，不能当身份用（§9-4） |
| `models_observed` | 已有 | 不变 |

- 采集实现：`probes/index.ts` 增一个解析 header 的函数，两个适配器（dsh-cli、web-ui）在切出 `fresh` 日志文本后对它再调一次——与现有 `collectFromJsonl(fresh)` 同一段文本，vendor 零改动。会话级字段（工具清单、系统提示）**取各轮里第一个非空值**（header 帧只随第 1 轮出现）。
- 落点：episode 级字段（EpisodeRecord 侧），不进 TurnRecord 逐轮重复存。
- 工具清单取观测值而不是从配置推导，原因是：模型可见的工具 = harness 内置工具 + 插件提供的工具 + skill 工具。配置文件推不全（bundle 盲区同 §2.1），header 里的才是生效值。
- 落库：`answers` 表增加 `tools_sha`、`system_prompt_sha`、`persona` 列（persona 供 §3 作轴取数，与 model/effort/agent 同路；schema v10，P1 一次建好，tools 列 P2 前保持 NULL）。

## 3. 对比轴与归因

- `views.ATTRS` 增加 `persona` 和 `tools`；`SUBJECT_FIELDS` 增加 `persona`；`follows()` 增加分支：**persona / tools 作轴 → 放行 subject 这一个 ATTR**（`DERIVED_ATTR` 不加新键——`persona↔subject` 会覆盖现有 `subject→model` 映射，且告警文案会错位；model/effort/agent/skills_* 现行路径不动）。
- `attr_value` 增加 `persona`、`tools` 两个分支（轴名与列名不同：tools 轴取 `tools_sha` 列，兜底 `str(row.get(name))` 取不到）；**NULL 统一成 `"?"`**，不再变成字符串 `"None"` 被当作正常取值参与分组。
  - **tools 轴遇到 `"?"` 行（旧 run 无 header 观测）时拦截**，提示「旧 run 无工具观测，tools 轴只对新 run 可用」——与决定 6 对上；
  - **persona 轴遇到 `"?"` 行（persona_sha 为空，来自 bundle 或缺失）时拦截**，提示「persona 取不到配置（bundle/缺失），无法对比」——与 tools 轴对称。
- persona 轴的取值是哈希：页面上展示为「dsh_profile 名 · 短 sha（前 8 位）」——**只改展示，不改分组与指纹**。
- **放行语义（与现行机制对齐）**：`follows(axis)` 只放行 axis 本身和 `subject` 两个 ATTR；其余 ATTRS（model、effort、agent、**persona**、skills_mode、skills_base、mode、evalset_version）逐一检查、不一致**拦截**。即：tools 作轴时 persona 或 model 混变会被拦下——这是对的；persona A/B 时 model 混变同样被拦下。
- **新增显式检查（现行机制的盲点）**：被 subject 放行**静默带过**的，是不属于 ATTRS 的 subject 字段——`plugins_sha`、`routing`、`skill_tool`、`model_provider`、`dsh_profile`。取数：`answer_view_rows` 带出 `runs.subject_json`（§10），对比与 Shapley 共用同一检查 helper：
  - `plugins_sha`：**非 tools 轴下必须一致，不一致拦截**——提示词 A/B 时一侧多装一个检索注入/记忆插件就是这种情况（决定 3 那类「改变模型输入」的集成代码，混进去就是混淆因素）。tools 轴下**跨轴值允许不同**（工具增减场景本意），但**同一轴值内必须一致**：同轴值内 tools_sha 相同而 plugins_sha 不同，说明变的是不暴露工具的集成代码，拦截。提示词类插件列入 `prompt_plugins`（§9-1）后进 persona_sha、不进 plugins_sha，不受此检查影响——**未列入的就落在这里被拦住**。
  - `routing`、`skill_tool`：不一致**拦截**——routing 直接决定加载哪个 skill、skill_tool 是加载工具名，都是改变会话行为的混淆因素。routing A/B 的出路见下条 subject 轴。
  - `model_provider`、`dsh_profile`：不一致**告警**——名称性字段，实际效果已由 model 与 eline 内容承载。
  - **axis（或 Shapley 因子）为 subject 时，跳过非 ATTR 字段检查**——subject 整体就是用来跨这些字段做对比的，routing A/B 的出路即在此；代价是这些字段的混变只受 subject_fp 分组约束，不再逐字段拦截。
- **Shapley 同步修通**：`shapley_cells` 的放行集合现在自算（`a not in {DERIVED_ATTR.get(f) for f in factors}`），不调 `follows()`——persona/tools 没有 DERIVED_ATTR 键，subject 不会被放行，作因子直接抛「组件之外未固定的属性取值不一致：subject」。改为**放行集合 = ∪ `follows(f)`**，非 ATTR subject 字段检查（含 subject 因子跳过）在 Shapley 里同一 helper 生效。「因子允许 persona 和 tools」至此才真的跑得通。
- `plugins_sha` **不作对比轴**（决定 2）。它随 subject 整体参与分组，集成代码变了会自动分成两组，不会混入结果。
- `shapley_cells` 的因子限制不变（k ≤ 3，两水平）。

典型用法：

- **提示词 A/B**：两个 eline profile 只有 persona 不同，对比页选 `persona` 轴；其余 subject 字段不一致会被上表检查拦下（plugins_sha 拦截正是防「顺手多装了个插件」）。
- **工具增减**：同 persona、同模型，插件清单增减一个提供工具的插件，对比页选 `tools` 轴；plugins_sha 跨轴值的变化放行，同一轴值内不一致拦截。
- **routing A/B**（如需）：拿 `subject` 整体作对比轴——跳过非 ATTR 字段检查，两侧本来就是两套被测配置。

## 4. 工具使用判定

### 4.1 用例写法（样例实例）

```markdown
## 路径
- 必须：加载 skill trade-payment 【轮次：1】
- 必须：调用 tool web_search 【轮次：2】【计分】【权重：20】
- 禁止：调用 tool pwsh
```

语义与「加载 skill」相同：

- 「必须」：截至第 N 轮（含）调用过；不写轮次指截至最后一轮。
- 「禁止」：第 N 轮调用即违反；不写轮次指全程任一轮调用即违反。
- forced 会话不判。

编译产物（样例）：

```json
{"type": "must", "action": {"kind": "call_tool", "tool": "web_search"}, "turn": 2}
```

check：

- **报错**：tool 名等于 skill 工具名（`subject.skill_tool`，缺省 `skill`）时，应写成「加载 skill」。
- **提示**：tool 名不在库内已观测的工具清单（answers 已落库 `tools_list` 的并集）中。没有观测数据时不提示。

### 4.2 判定

- `scoring/items.py`：`EpisodeContext` 增加 `tools_by_turn`，由 `build_context` 从 `observations.tools` 取。
- `scoring/operators.py`：路径算子按 `action.kind` 分派。现有 `load_skill` 编译形态**字节级不动**（item_sha 载荷已含整个 action，`kind: "load_skill"` 已在——存量条目 sha 零变化，作为测试断言）；新增 `call_tool` 分支；算子升 `skill-path@2`。
- **升版本的代价（先说破）**：chain 的 canonical 含 `op.id@op.version`，chain_sha 随之变化 → **全部答案进入待重判**（页面「待重判 N 段」等于全量）。影响可控：LLM 算子有 VerdictCache，命中缓存不产生新的模型调用；人工改判按 item_sha + answer_sha 存，不受影响。
- 节点表和默认规则不变：路径违反触发否决（doc/17 §6.2），`SCALES["path"]` 复用（满足/违反/不适用）。

### 4.3 本期不做

- 参数是否正确、调用结果是否被采信。后续可以写成事实条目，交 judge 判，例如「回答采用了 web_search 返回的报价」。不新增节点。
- tool 返回值是否正确：归自动化测试（决定 2、4）。

### 4.4 评测集

本方案只交付判定机制。机制验证用例（§9-2）挂 mapping.yaml 已有的「工具调用: tc」维度，词表不动；正式评测集何时起另定。

## 5. 成本口径

- **tokens 口径沿用 collector 现行 total**：`tokens_total = input + output + reasoning`；cacheRead 不计入（多步会话里重复读回的缓存命中，全额累加会让总量随步数膨胀——collector.ts 既有口径与注释）。`tokens_cache_read` 单列备查。展示注明口径，避免「−48%」类结论陷入 cache 计费争议。
- 来源：EpisodeRecord 顶层已有聚合 `usage`（steps、tokens）与 `duration_ms`，ingest 直接取，不逐轮重算。
- 落库：`answers` 增加 `tokens_total`、`tokens_cache_read`、`steps`、`duration_ms` 列（schema v10，P1 一次建好）。
- 不进计分，不进 `scoring_fp` 和 `rules_sha`。
- `compare_scores` 输出增加成本差：同题配对差的中位数作点估计，区间沿用按用例重采样的**配对自助法**。实现约束：`_bootstrap` 是固定种子、按位置抽样，**成本序列与分数序列必须按同一个用例顺序、同样长度传入**，两者抽到的样本才一致（一次重采样同时出分数差与成本差）。
- 对比页结果表增加两列（tokens 差、耗时差）。结论样例：「分数 −1（区间跨 0），tokens −48%，耗时 −35%」。

## 6. Harness（本期只定契约，不做实现）

新 harness 接入就是实现 `ports.AgentAdapter`。为保证结果可比，适配器必须产出：

| 产出 | 用途 | 缺失时 |
| --- | --- | --- |
| 每轮 output | 判定 | 不能接入 |
| skills（加载与 sha） | 路径约束、注入观测 | 在 `AdapterCapabilities` 声明，skill 路径条目判「不适用」 |
| tools（name、args） | 工具路径约束 | 同上 |
| 工具清单、系统提示 | §2.2 观测 | 观测字段为空，`tools` 轴不可用 |
| usage、model | 成本、有效模型核对 | 成本列为空 |

- **能力门控的落点**：`AdapterCapabilities` 增 skills/tools 观测能力声明，随 `RunManifest.agent.capabilities` 落库；判定链可读（EpisodeContext 增字段或 ingest 落列）。观测能力缺失时路径条目**两个方向都判「不适用」**——现状 SkillPathOperator 对 observations 缺失：「必须」分支假「违反」、「禁止」分支假「满足」，都要改。
- harness 内置的系统提示和内置工具随 `agent.version` 变化，归入 agent 身份，不单独拆。
- 上下文压缩、子 agent 仍按 2026-10-22 的决定暂缓。

## 7. 前置：计分逻辑版本（已实现）

- 状态：**已实现**（定稿时随基线一并提交推送）：`scoring/rules.py` 的 `SCORING_LOGIC_VER`（整数，现值 1）经 `rules_record` 并入 `rules_sha`；`cli.py`/`serve.py` 入库已接 `rules_record`；`tests/test_serve.py` 已覆盖。
- 规则：任何会改变已有会话结论的计分代码改动（计分单位、否决、取整、维度聚合）必须升 `SCORING_LOGIC_VER`。旧结论随 `rules_sha` 失效，页面 `needs_rescore` 自动提示（按当前 rules_sha 查 conclusions 是否存在）。
- 原因：组件对比是跨时间进行的，计分代码修复后，旧结论不能和新结论混在一起比（10-30 复核发现）。
- 失效链独立：本方案 §4 的 `skill-path@2` 属**算子版本**（chain_sha 维度，代价见 §4.2），不改计分逻辑，不动 `SCORING_LOGIC_VER`。算子版本与计分逻辑版本两条失效链各自独立生效。
