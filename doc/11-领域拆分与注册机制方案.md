# 11 领域拆分与注册机制方案：面向插件与 skill 测评的结构化设计

v1（2026-10-24）· 基线 `main` 84c48b7 · 设计方案（不含实现）

## 0. 为什么现在做

当前项目是一个分层清楚、有测试与数据版本管理的**单机内部工具**：runner（TS，约 3.4k 行）执行与观测，md2case（Python，约 1.3k 行）编译用例，scoring（Python，约 3.1k 行）判定、存储、复核，测试约 4.2k 行。它测的是**一个固定对象**（ElineAI agent + Profile），用**一套固定口径**（6 类条目、一个会话结论函数）。

下一阶段要测评**用户上传的插件和 skill**。这会同时打开四个维度的「可变」：

| 可变 | 现在 | 将来 |
| --- | --- | --- |
| 被测对象 | agent + Profile（知识库只是 Profile 的一个属性） | agent 配置、skill、插件……都是一等对象，可上传、有版本 |
| 用例与类目 | 4 个维度（kr/mt/sc/ec），由 `mapping.yaml` 登记 | 新类目：触发准确率、工具调用、格式、安全……；上传者自带用例 |
| 指标 | 条目结论词 → 会话通过/失败（doc/10 后为会话分） | 结构化指标：触发召回/精确、工具错误率、token 成本、耗时、稳定性、相对基线的增益 |
| 评分方案 | 一个函数、全局一套 | 按类目、按被测对象类型注册不同评分方案 |

所以要先**拆分领域**，并给每个会被扩展的地方定义**统一的注册机制**。这份方案回答三件事：领域怎么拆（§1）、哪些地方需要注册以及怎么注册（§2–3）、测评上传对象的流程与演进路线（§4–6）。

## 1. 领域划分

```
            ┌────────────┐      ┌────────────┐
            │ 被测对象域  │      │  用例域     │
            │ Subject    │      │ Case       │
            └─────┬──────┘      └─────┬──────┘
                  │  对象版本 + 用例版本 → 执行计划
                  ▼                    ▼
            ┌───────────────────────────────┐
            │ 执行域 Execution（含观测）       │ → EpisodeRecord + 观测
            └───────────────┬───────────────┘
                            ▼
            ┌────────────┐     ┌────────────┐     ┌────────────┐
            │ 判定域      │ ──▶ │ 评分域      │ ◀── │ 复核域      │
            │ Judging    │     │ Scoring    │     │ Review     │
            └────────────┘     └─────┬──────┘     └────────────┘
                                     ▼
                            ┌────────────────┐
                            │ 结果与分析域     │  比较、贡献、报表、榜单
                            └────────────────┘
       横切：注册中心（Registry）· 契约与指纹（Schema/Fingerprint）· 平台（API/作业/权限，后期）
```

| 领域 | 职责 | 核心概念 | 现有代码 | 现在的问题 |
| --- | --- | --- | --- | --- |
| **被测对象** | 被测对象的类型、上传、清单、版本、物化到执行环境 | Subject、SubjectType、SubjectVersion（内容哈希）、Binding（一次 run 装配了哪些对象） | `runner/src/profile.ts`、`materialize.ts`、`tools/export-skills.mjs` | 只有 Profile 是对象；skill 是 Profile 的 `skills_roots` / `skills_base` 属性，没有身份与版本 |
| **用例** | 用例编写、编译、类目、变体、注入点、评测集版本、题目指纹 | Case、Category（维度）、Section、Variant、InjectionPoint、Evalset | `evalset/md2case.py`、`mapping.yaml`、`knowledge/`、`scoring/items.py` 的指纹部分 | 类目与段落已配置化；但用例只能指向「agent」，不能声明针对哪个对象 |
| **执行** | 规划、驱动、干预、会话执行、观测采集、运行清单 | Plan、Driver、Adapter、Intervention、Probe、EpisodeRecord、RunManifest | `runner/src/*`（`ports.ts` 已定义驱动/适配器/干预/探针接口） | 观测键固定在 `Observations` 接口；无隔离执行（上传代码不可信） |
| **判定** | 把一条期望判成结论 | ItemType、Operator、Chain、Verdict、VerdictCache | `scoring/items.py`、`operators.py`、`chain.py` | 算子已可插拔；**条目类型写死**（6 类散在约 20 处） |
| **评分** | 指标计算、评分方案、会话/题目/维度/综合分、否决与及格 | Metric、Measure、Rubric、Conclusion | `scoring/policy.py`、`views.py` | **只有一套口径**；runner 采集的 token/步数/耗时/工具错误从未进入评分 |
| **复核** | 人工打分、改判、抽检、作废 | Review、Override、Queue、Sampling | `scoring/store.py`（reviews）、`serve.py` | 绑定在「条目」上；数值指标不可复核 |
| **结果与分析** | 存储、比较轴、组件贡献、导出、报表 | ResultStore、CompareAxis、Contribution、Report | `scoring/store.py`、`views.py`、`cli.py` | 评测库表结构绑定在条目结论上；没有通用的指标值表 |

**领域之间只通过数据契约交互**（§3.3）：被测对象域给出「对象版本 + 物化方式」，用例域给出「编译行」，执行域产出「EpisodeRecord + 观测」，判定域产出「Verdict」，评分域产出「Measure + Conclusion」，复核域产出「Review」。跨语言边界（TS runner ↔ Python scoring）现在是隐式 JSON，改为版本化的 JSON Schema。

## 2. 需要注册的扩展点

| # | 注册项 | 归属领域 | 注册什么 | 现状 | 上传对象测评时的例子 |
| --- | --- | --- | --- | --- | --- |
| R1 | **被测对象类型** SubjectType | 被测对象 | 打包格式、清单字段、静态检查、物化方式（如何装进一次会话）、身份（内容哈希） | 无 | `skill`（SKILL.md + 资源目录）、`plugin`（含代码/工具声明）、`agent-profile` |
| R2 | **驱动 / 适配器** Driver/Adapter | 执行 | 如何启动会话、发消息、取轨迹；能力声明 | 已有接口（`ports.ts`：dsh-cli、web-ui、scripted） | 容器沙箱驱动 |
| R3 | **干预** Intervention | 执行 | 注入方式、强制/自然模式 | 已有接口（k-v 替换） | 「禁用某 skill」「替换为基线版本」用于增益对照 |
| R4 | **探针** Probe | 执行 | 观测键、观测值 schema、从轨迹提取的方法 | 已有接口；`Observations` 键固定 | 插件工具调用、副作用（文件/网络）、错误类型 |
| R5 | **类目** Category | 用例 | 维度名、id 前缀、必填段落、主口径、默认评分方案 | `mapping.yaml` 的 `dims` 部分已登记 | 触发准确率、工具调用正确性、安全拒答 |
| R6 | **条目类型** ItemType | 判定 | 取值集、两点求值的有利/不利值、评分角色（门槛/否决/计分/只记录）、从用例中提取的规则、对应的用例段落 | **写死** 6 类 | 「应调用工具 X」「不应产生副作用 Y」「输出符合格式 Z」 |
| R7 | **判定算子** Operator | 判定 | 契约（id、version、source、scales、inputs、judge）；可选输出分数 | 已有（内置登记 + `模块:类名` 引用） | 针对某个插件的工具调用判定器、LLM 判定 |
| R8 | **指标** Metric | 评分 | id@版本、作用层级（轮/对话/题目/对象）、值类型（结论词/数值/是否）、来源（探针/算子/人工/派生）、方向、单位、汇总方式 | 无（只有隐含的通过率） | `trigger.recall`、`tool.error_rate`、`cost.tokens`、`latency.p50`、`stability` |
| R9 | **评分方案** Rubric | 评分 | 被评对象（类目/对象类型/具体对象）、选取哪些对话、指标与权重、数值指标的归一化、门槛与否决、及格线 | 一个函数 + policy.yaml | 「skill 通用方案」「插件通用方案」「某上传者自定义方案」 |
| R10 | **测评套件** Suite | 用例 | 一组用例 + 适用的对象类型 + 默认评分方案 + 对照设计（有/无对象） | 无（评测集是全量的） | 「skill 触发套件」「插件工具调用套件」「上传者自带套件」 |
| R11 | **报表视图** View | 结果与分析 | 报表/榜单的定义 | 写在 serve 路由里 | 对象详情页、榜单（后期） |

R2–R4、R7 已经有接口，只需统一到 §3 的注册约定；R1、R6、R8、R9、R10 是新增；R5 从 `mapping.yaml` 提升为正式注册项。

## 3. 统一注册约定

### 3.1 每个注册项都有一份清单

```yaml
kind: metric                 # 注册项类别：subject_type | probe | category | item_type | operator | metric | rubric | suite | …
id: trigger.recall
version: 1                   # 语义变化必须升版本；文案、注释变化不升
title: 触发召回
entry: scoring.metrics.builtin:TriggerRecall   # 代码实现（可选；纯配置项没有）
params: {}                   # 参数，按该类别的参数 schema 校验
requires: [probe:skills@1, item_type:path@1]   # 依赖的其他注册项（含版本）
compat: {record_schema: ">=3"}                 # 适用的数据契约版本
```

| 约定 | 说明 |
| --- | --- |
| **来源分三级** | 内置（随代码发布）· 仓库配置（`registry/*.yaml`，团队维护）· 上传（用户提交，进入隔离与审核流程，§4） |
| **校验在加载时** | 参数 schema、依赖是否存在、版本兼容；不合法拒绝加载，不在运行中途失败（沿用 `chain.config_from_dict` 的做法） |
| **指纹** | 每个注册项算内容指纹（清单 + 实现版本）；一次评分用到的全部注册项组成**配置指纹**，进入取数键。这是现有 `chain_sha` 的推广：判定配置、指标配置、评分方案各自一个指纹，结论按（期望、判定配置、评分配置）分键，任何定义变了都不会和旧结果混在一起 |
| **登记入库** | 用到的注册项清单与指纹写进评测库 `registry_items` 表，结果可追溯到当时的定义 |
| **版本规则** | 改了判定/计算语义 → 升版本；只升版本、不覆盖旧版本；旧结果按旧版本可复现 |

### 3.2 代码组织

保持单仓库（monorepo），按领域拆目录与包，不拆服务：

```
schemas/            数据契约（JSON Schema，带版本）：case-row、episode-record、observation、verdict、measure、conclusion
registry/           仓库级注册清单（*.yaml）
evalset/            用例域：md2case、mapping（类目、段落）、knowledge、suites/
runner/             执行域（TS）：drivers、adapters、interventions、probes、subjects/（物化）
evalcore/           横切（Python）：注册中心、指纹、契约校验、领域模型
judging/            判定域：item_types/、operators/、chain
scoring/            评分域：metrics/、rubrics/、口径计算
review/             复核域：服务、模板、静态资源
results/            结果与分析域：store（评测库）、比较、贡献、导出
```

迁移方式：先在现有 `scoring/` 内按子模块拆（`scoring/judging/`、`scoring/metrics/`…），接口稳定后再提升为顶层包；每一步保持测试全绿。

### 3.3 数据契约

| 契约 | 生产方 → 消费方 | 现状 | 改为 |
| --- | --- | --- | --- |
| 编译行 CaseRow | 用例 → 执行、判定 | md2case 输出，schema 2 | JSON Schema；新增 `targets`（针对哪些对象/对象类型） |
| EpisodeRecord | 执行 → 判定、评分 | TS 接口，schema 3；Python 侧按字典读取 | JSON Schema，两侧做契约测试；新增 `bindings`（本会话装配的对象版本） |
| Observation | 探针 → 评分 | `Observations` 固定键 | `observations: {probe_id@ver: value}`，值按探针声明的 schema 校验 |
| Verdict | 判定 → 评分、复核 | verdicts 表 | 不变，加 `score`（doc/10） |
| Measure | 评分 → 结果 | 无 | 新增：`(answer_id, metric_id@ver, scope, turn, value_num, value_text, source, config_sha)` |
| Conclusion | 评分 → 结果、复核 | conclusions 表 | 加评分方案维度：`(answer_id, judge_fp, chain_sha, rubric_sha) → score / range / status` |

## 4. 测评上传的插件与 skill

### 4.1 流程

```
上传 → 静态检查 → 登记（内容哈希、版本） → 选择套件与评分方案
     → 生成执行计划（有/无对象对照） → 沙箱执行 → 判定 → 评分 → 抽检复核 → 报告
```

| 阶段 | 内容 | 所在领域 / 注册项 |
| --- | --- | --- |
| 上传 | 包 + 清单（名称、版本、类型、声明的触发描述/工具/权限） | 被测对象 / R1 |
| 静态检查 | 清单字段、大小与格式、禁用内容、声明权限是否越界、依赖 | 被测对象 / R1 |
| 登记 | 内容寻址存储；同内容同身份；版本链 | 被测对象 |
| 选择套件 | 按对象类型匹配通用套件（如 skill 触发套件）+ 上传者自带用例（单独标记、不进公共统计）+ 隐藏留出集 | 用例 / R10 |
| 执行计划 | 每道题跑「装配该对象」与「不装配（或装配基线版本）」两组，用于计算增益；trial ≥ 2 测稳定性 | 执行 / R3 |
| 沙箱执行 | 每会话独立物化（现有 bundled-copy 模式即逐会话物化 skill 副本，是基础）；含代码的插件需容器隔离、网络与资源限制、无凭据 | 执行 / R1、R2 |
| 判定与评分 | 条目判定 + 探针指标 → 按该对象类型的评分方案出分 | 判定、评分 / R6–R9 |
| 复核 | 低置信与分歧样本进入人工抽检 | 复核 |
| 报告 | 对象得分、各指标、相对基线的增益、稳定性、与历史版本对比 | 结果与分析 / R11 |

### 4.2 skill 与插件的指标示例

| 指标 | 层级 | 类型 | 来源 | 说明 |
| --- | --- | --- | --- | --- |
| `trigger.recall` | 对象 | 比例 | 探针 skills + 用例「应加载」 | 该加载时加载了的比例（路径约束「必须」的推广） |
| `trigger.precision` | 对象 | 比例 | 探针 skills + 用例「不应加载」 | 不该加载时没加载的比例（防止 skill 抢触发） |
| `answer.session_score` | 对话 | 数值 0–100 | 判定 + 评分 | doc/10 的会话分 |
| `uplift.session_score` | 对象 | 数值 | 派生 | 装配与不装配两组的会话分之差（doc/10 组件贡献的单组件形式） |
| `tool.call_accuracy` | 对话 | 比例 | 探针 tools + 判定 | 插件：应调用的工具调用了、参数正确 |
| `tool.error_rate` | 对话 | 比例 | 探针 tool_errors | 插件工具报错比例 |
| `cost.tokens` / `latency.p50` | 对话 / 对象 | 数值 | 探针 usage、轮次耗时 | 成本与时延，越小越好 |
| `stability` | 题目 | 比例 | 派生 | 多次 trial 结论一致的比例 |
| `safety.refusal` | 对话 | 结论词 | 判定 | 越权请求是否拒绝 |

数值指标进入评分方案时按方案声明的方式归一到 0–100（如线性：达到 `target` 得 100、达到 `worst` 得 0）。

### 4.3 评分方案示例

```yaml
kind: rubric
id: skill.default
version: 1
subject: {type: skill}                    # 适用于所有 skill；也可写 {type: skill, id: trade-documents}
select:
  suites: [skill.trigger@1, owner-cases]  # 上传者自带用例只用于该对象报告，不进公共统计
  compare: {without_subject: true}        # 生成对照组
metrics:
  - {metric: trigger.recall@1,       weight: 2}
  - {metric: trigger.precision@1,    weight: 1}
  - {metric: uplift.session_score@1, weight: 3, normalize: {target: 15, worst: -5}}
  - {metric: cost.tokens@1,          weight: 0.5, normalize: {target: 4000, worst: 12000}}
vetoes:
  - {metric: safety.refusal@1, when: "未拒答", action: zero}
pass_mark: 60
```

### 4.4 上传带来的非功能要求

| 项 | 要求 |
| --- | --- |
| 隔离 | 上传内容一律视为不可信：只在沙箱执行，不在复核机或评测库所在机器运行；无凭据、限制网络 |
| 防刷分 | 公共套件之外保留隐藏留出集；上传者自带用例不进公共统计 |
| 成本 | 每次提交的会话数、token 预算有上限；判定缓存跨提交复用 |
| 多租户 | 上传者身份、可见性、配额；结果按提交归档 |
| 隐私 | 真实会话日志不进仓库与公共报表（仓库现为可匿名访问，`tests/fixtures` 含真实日志，需先处理） |

## 5. 演进路线

| 阶段 | 内容 | 形态 | 何时开始 |
| --- | --- | --- | --- |
| **P0 注册内核** | `evalcore` 注册中心与清单校验、指纹；R6 条目类型、R8 指标、R9 评分方案注册化；`measures` 表；doc/10 的百分制作为默认评分方案实现在其上 | 单机，配置文件注册 | 现在（与 doc/10 合并实施，见 §6） |
| **P1 skill 一等对象** | R1 被测对象类型（先 `skill`、`agent-profile`）；运行清单记录 bindings；R10 套件；`trigger.*`、`uplift.*` 指标；有/无对照计划 | 单机，仓库内 skill（可信来源） | P0 完成后 |
| **P2 插件与结构化观测** | `plugin` 对象类型；R4 探针键开放、Observation 契约；工具调用、副作用、成本指标；容器沙箱驱动 | 单机 + 沙箱执行 | 确定插件格式后 |
| **P3 上传测评平台** | 上传与静态检查、内容寻址存储、作业队列、API 服务、多用户复核（PostgreSQL，09 §9 已预留）、权限与配额、报告与榜单 | 服务化 | 开放给外部上传前 |

P0–P2 不改变「单机、命令行 + 本地服务」的形态；只有 P3 才需要服务化。

## 6. 与 doc/10 的关系

doc/10 第 1 步把百分制直接写在 `policy.py` 里（6 类条目、一套口径）。若按本方案演进，这部分在 P0 会被注册化的条目类型与评分方案取代，等于改两次。建议：

1. **doc/10 的页面与交互（第 2–4 步）不变**：评分表、结论条、对话面板、四个页面都与注册机制正交。
2. **doc/10 第 1 步改为在 P0 之上实现**：先做条目类型注册（6 类内置条目改为注册项，带评分角色）、指标与评分方案注册、`measures` 表；百分制会话分作为内置评分方案 `session.default@1`。
3. 复核页的评分表按评分方案渲染：门槛/否决/计分/只记录四种角色决定分节与说明文字，新条目类型不需要改页面。

调整后的顺序：P0（含 doc/10 口径）→ doc/10 第 2–4 步 → P1 → P2 → P3。

## 7. P0 的具体改动（概要）
