# Agent_Eval 评测结果管理改造方案

版本：v1（2026-10-23）
基线：代码 `99279ea`，设计 08-判定算子扩展方案 v2

## 1. 背景与目标

08 方案 v2 已经落地：判定拆成了算子链，人工改判改为覆盖层，复核服务也已上线。这一轮评估发现三类问题，本方案把它们合并处理：

1. **结论正确性缺陷**：组内成员判"错"没有否决会话；未决条目把本可确定的会话也排除出了分母；算子异常被当成未决处理。
2. **答案按 run 组织，不便比较**：同一道题的答案散落在各个 run 里，比较时要临时拼接。复核服务每次请求都全量重算，题目视图还会把不同评测集版本的 run 混在一起。
3. **期望修订后旧答案无法复用**：判定结论绑定在 run 目录里，期望一改，就只能重新跑 agent。

改造目标：

| # | 目标 | 说明 |
| --- | --- | --- |
| G1 | 修复结论缺陷 | 新旧对拍覆盖组内"错"；未决和异常只在可能改变结论时才影响会话 |
| G2 | 以题目和题组管理答案 | 答案归到题目下，任意属性（模型、干预、skill 版本、评测集版本）都可以作为比较轴 |
| G3 | 支持旧答案重判 | 输入不变、期望修订时，按新期望重判已有答案，不重新跑 agent |
| G4 | 评测库存储 | 判定和人工数据存入 SQLite 评测库，作为唯一事实来源；原始运行产物仍是不可变文件 |
| G5 | 复核服务按题目组织并可扩展到正式规模 | 所有视图从评测库取数并分页，不再全量重算 |
| G6 | 预留演进路径 | 存储层隔离，日后可以接入 DuckDB 做分析，或迁移到 PostgreSQL |

范围外：编译器、执行器、用例结构不改；模型算子（llm-fact 等）仍按 08 方案第二批实施；并发复核不考虑。

## 3. 结论缺陷修复（C1–C5）

这部分不依赖存储改造，在现有代码上先行修复。

### 3.1 C1：组内成员判"错"

旧实现中，所有必要事实（包括组成员）里只要出现"错"，会话就失败（`CONTRA in v.facts.values()`）。新实现只检查组内有没有满足的成员，于是"组内一错一对"从 fail 变成了 pass，同时违反了 08 §7 第 4 步。

修复：任一必要事实为"错"即判失败，不论它是单条还是组成员，也不受 `veto_on_forbidden` 控制（这个开关只管禁止事实）。

补充对拍用例：组内一错一对、组内一错一未提及、单条为"错"且同时有禁止事实被采信。

### 3.2 C2：未决条目只在可能改变结论时生效

现行做法是：参与判定的条目中只要有未决，会话就记为 undecided。但有些未决条目根本改变不了结论，例如同组已有成员满足、关闭否决时的禁止事实。

改为**两点求值**：把所有未决条目分别取最有利和最不利的值，各算一次会话结论：

| 条目 | 最有利 | 最不利 |
| --- | --- | --- |
| 必要事实 | 对 | 错 |
| 禁止事实 | 未采信 | 采信 |
| 前提 | 成立 | 不成立 |
| 路径 | 满足 | 违反 |
| 拒答 | 拒答 | 未拒答 |

两次结论相同，就是确定结论；不同，会话记为 undecided，再按 `policy.undecided` 处理。期望事实不参与结论，不进入求值。

两点求值足够：前提确定时，会话结论随条目取值单调变化（只会从 fail 变为 pass）；前提未决时，最不利取值得到 invalid，最有利取值不可能是 invalid，两者必然不同，会话正确地落入未决。

### 3.3 C3：算子异常与未决分开

08 §4.1 规定算子异常记为 error，不计入分母。现在 error 行的机器结论为空，被口径层当成未决处理，于是 `undecided: fail` 时会被计为失败。

修复：error 条目同样参与两点求值。如果结论因 error 条目而无法确定，会话记为 **error**，不计入分母，也不受 `policy.undecided` 影响；未决和异常同时存在时，以 error 为准。结论能够确定时，error 条目不影响会话。

### 3.4 C4、C5 及其他

- **C3（改判接口）**：`/api/review` 现在先写 `review.jsonl`，再检查会话是否存在，导致返回 400 时改判已经落盘。改为先校验，再写入。存储改造后，这一步放进同一个事务里完成。
- **C4**：`vendor/dsh-kernel.ts` 的 `splitDshBin` 加了双引号路径支持，但没有记进 `UPSTREAM.md` 的本地补丁。不补上，下次同步上游时这个改动会被静默覆盖。
- **C5**：04 §7 第 3 类出口要求"变体泄露嫌疑清单"，质量视图里没有。按 CASE-STRUCTURE §8 的提示规则，用编译行中关键条件的关键词和轮次复算：被替换的那一轮缺少本轮条件的关键词，或者包含了更早轮次条件的关键词。
- `Index.update_episode` 的锁只包住了一行赋值。这个类在 C13 中会被删除，不单独修。

## 4. 以题目为主轴的组织（C6）

### 4.1 题目身份与两个指纹

只靠 uid 不足以确定"同一个问题"：评测集改版后 uid 不变，但内容可能已经改了。每道题从编译行计算两个指纹：

| 指纹 | 计算字段 | 决定什么 |
| --- | --- | --- |
| 输入指纹 `input_fp` | `history`、用户消息序列（`turns` 中 role 为 user 的内容，按顺序）、`injections`（point、option、rev、file、key、value） | 回答能否直接比较 |
| 判定指纹 `judge_fp` | `answerable`、前提、事实（id、kind、text、keywords、turn、group）、路径约束 | 判定结论能否直接比较 |

- **题目身份** `qkey = uid + "|" + input_fp`。
- 参考答案、备注、证据、标签、状态、关键条件的改动不影响任何指纹。
- 指纹是对规范化 JSON（键排序、UTF-8）取 sha256 前 16 位，在 `scoring/items.py` 中计算，不改编译器。

条目级还有一个**条目指纹** `item_sha`，用于判断人工改判是否仍然有效（第 6.3 节）：

| 条目 | 计算字段 |
| --- | --- |
| 事实、前提 | kind、text、turn |
| 路径 | type、action、turn |
| 拒答 | 常量 |

关键词和组不进入条目指纹：它们影响规则判定，但不影响人对"这条事实是否成立"的判断。

### 4.2 三层组织

| 层级 | 单位 | 用途 |
| --- | --- | --- |
| 题目 | `qkey` | 比较同一问题下不同模型、skill 版本、干预、trial、评测集版本的回答 |
| 题组 | 用例 id，即种子 `#0` 和它的全部变体 | 同义请求一致性：同一配置下对一组改写的回答是否一致 |
| 自定义分组 | 维度、主题、标签、pair | 按条件动态筛选，不单独存储 |

答案挂在题目下，带有以下比较属性：

| 属性 | 来源 |
| --- | --- |
| profile、模型 | `run.json` 的 profile id、`models_observed` |
| 干预 | EpisodeRecord 的 `mode` |
| trial | EpisodeRecord 的 `trial` |
| skill 环境 | 环境快照的 `skills_mode`、`skills_base` |
| 评测集版本 | 环境快照的 `evalset` |
| run | `run_id` |

### 4.3 题目级统计（C12）

统计均按题目的**当前期望**（第 5 节）和当前链配置下的有效结论计算，只计 pass 或 fail 的答案。

| 统计 | 定义 | 用途 |
| --- | --- | --- |
| 难度 | 1 − 全部答案的通过率 | 找出过难或过易的题 |
| 区分度 | 各模型通过率的极差（最大值 − 最小值），至少要有 2 个模型 | 区分度为 0 的题对比较模型没有贡献 |
| 稳定性 | 同一模型、同一干预下，多次 trial 结论一致的比例 | 不稳定说明题目有歧义或判定不稳 |
| 题组一致性 | 同一模型、同一干预下，种子与非诱导变体的结论一致率 | 同义请求一致性（08 待定事项 #5 的默认口径） |
| 历史 | 同一模型在不同 skill 环境或时间点上的通过率序列 | 观察知识修订、模型升级前后的变化 |

改写类型为"诱导"的变体不计入题组一致性（CASE-STRUCTURE §2.13）。题组一致性的口径仍属待定，以上是默认实现（第 13 节）。

## 5. 当前期望与旧答案重判（C7）

### 5.1 当前期望

同一题目（相同 `qkey`）在不同评测集版本中可能有不同的判定指纹。每道题记录一个**当前期望**：

- 导入一个评测集（`specs import <dist.jsonl>`）时，其中每一行的期望登记到对应题目下，并成为该题的当前期望。
- 输入改了的题会产生新的 `qkey`，与旧题目并存，答案不会混在一起。
- 新评测集里没有出现的题（退役或降级移出）保留最后一份期望，标记为非活跃。
- 可以用 `specs set-current` 显式指定某个版本的期望为当前期望。

答案入库时，执行那次 run 所用的期望也会登记进来。

### 5.2 重判

```text
python -m scoring rejudge [--question <qkey>] [--run <run_id>]
```

对所有"缺少当前期望 + 当前链配置下的判定"的答案补判，只调用算子，不运行 agent。

- 规则算子成本低，直接重算；模型算子经判定缓存去重（第 6.2 节）。
- 判定结果写入新行，旧期望、旧链配置下的结论全部保留，可以比较规则或 judge 版本之间的差异。
- 复核服务不触发重判，只在页面上提示"待重判 N 条"，并给出对应命令。

## 6. 评测库存储（C8–C10）

### 6.1 三层存储

| 层 | 载体 | 内容 | 规则 |
| --- | --- | --- | --- |
| 原始层 | 文件 | `results.jsonl`、`run.json`、session 日志 | 执行器产出，不可变 |
| 评测库 | SQLite 单文件，默认 `archive/eval.db` | run 登记、题目、期望、答案、条目判定、人工改判、判定缓存、会话结论 | 判定和人工数据的唯一事实来源 |
| 导出层 | jsonl、CSV、scoring.json | 判定明细、人工改判、聚合报告 | 用于审计、备份、CI，可随时重新生成 |

- 08 v2 的原则"文件是唯一数据源，SQLite 只做索引"调整为：**原始运行产物是文件，判定和人工数据以评测库为准**。
- 答案入库时保存完整的 EpisodeRecord。run 目录被移走或删除后，答案仍然保留，可以继续重判。
- 评测库开启 WAL 模式，复核服务读取时，命令行可以同时写入。
- 评测库里有真实业务对话，`archive/` 加入 `.gitignore`。

### 6.2 表结构

只使用标准 SQL 类型和语法，以便日后迁移（第 9 节）。

```sql
CREATE TABLE meta(key TEXT PRIMARY KEY, value TEXT);             -- schema_version 等

CREATE TABLE runs(
  run_id TEXT PRIMARY KEY, run_dir TEXT, evalset_version TEXT, profile_id TEXT,
  snapshot_json TEXT, imported_at TEXT);

CREATE TABLE questions(
  qkey TEXT PRIMARY KEY,                     -- uid|input_fp
  uid TEXT, case_id TEXT, variant_index INTEGER, rewrite TEXT,
  dim TEXT, topic TEXT, tags_json TEXT, input_fp TEXT,
  current_judge_fp TEXT, active INTEGER, first_seen TEXT);

CREATE TABLE specs(
  qkey TEXT, judge_fp TEXT, spec_json TEXT, evalset_version TEXT, imported_at TEXT,
  PRIMARY KEY(qkey, judge_fp));

CREATE TABLE answers(
  answer_id TEXT PRIMARY KEY,                -- run_id/episode_id
  qkey TEXT, run_id TEXT, episode_id TEXT, judge_fp_at_run TEXT,
  profile_id TEXT, models_json TEXT, mode TEXT, trial INTEGER,
  skills_mode TEXT, skills_base TEXT, evalset_version TEXT,
  run_status TEXT, record_json TEXT);

CREATE TABLE verdicts(                       -- 机器结论
  answer_id TEXT, judge_fp TEXT, chain_sha TEXT, item_id TEXT,
  kind TEXT, turn INTEGER, item_sha TEXT, answer_sha TEXT,
  value TEXT, source TEXT, operator TEXT, reason TEXT, trace_json TEXT,
  status TEXT, judged_at TEXT,
  PRIMARY KEY(answer_id, judge_fp, chain_sha, item_id));

CREATE TABLE reviews(                        -- 人工改判，只追加
  review_id INTEGER PRIMARY KEY,
  answer_id TEXT, item_id TEXT, item_sha TEXT, answer_sha TEXT,
  value TEXT, reason TEXT, reviewer TEXT, at TEXT);

CREATE TABLE verdict_cache(
  cache_key TEXT PRIMARY KEY, value TEXT, source TEXT, operator TEXT, reason TEXT);

CREATE TABLE conclusions(                    -- 派生表，可随时重算
  answer_id TEXT, judge_fp TEXT, chain_sha TEXT, policy_sha TEXT,
  status TEXT, reason TEXT, detail_json TEXT,
  PRIMARY KEY(answer_id, judge_fp, chain_sha, policy_sha));
```

索引：`answers(qkey)`、`answers(run_id)`、`verdicts(answer_id, judge_fp, chain_sha)`、`reviews(answer_id, item_id)`、`conclusions(judge_fp, chain_sha, policy_sha)`。

- `chain_sha` 是 operators.yaml 中**链配置**的哈希。期望或链配置任一变化都写新行，旧结论保留。
- 判定缓存的键规则不变（算子 id@版本 + 声明输入的哈希），从 `verdict-cache.jsonl` 迁入 `verdict_cache` 表。

### 6.3 有效结论（C9）

`effective_final` 的语义不变，取数改为从评测库读取：

```text
有效结论(答案, 条目, 期望, 链配置) =
    该答案、该条目上最后一条有效人工改判
    ?? verdicts 表中 (答案, 期望, 链配置, 条目) 的机器结论
```

人工改判有效，需要同时满足：

1. `answer_sha` 与条目所在轮的当前回答一致；
2. `item_sha` 与当前期望中该条目的指纹一致；
3. 取值在该条目类型的 scale 内。

第 2 条是新增的。这样期望修订时，只有文本被改过的条目上的人工结论失效，其余条目的改判照常沿用。人工改判不绑定期望或链配置：它是人对"这个回答是否满足这条事实"的判断，与机器用什么算子无关。

### 6.4 会话结论物化（C10）

总览要对全部答案做聚合，每次请求都重算的代价会随规模增长。会话结论物化到 `conclusions` 表：

- 主键包含期望、链配置、口径哈希，任一变化都会产生新的结论集。
- `rescore` 只重算这张表，不调用任何算子。
- 人工改判提交时，在同一事务内重算该答案的结论行。
- 重判完成后，重算受影响答案的结论行。

## 7. 比较（C11）

### 7.1 比较轴

08 v2 的"预期变量"（model、skill）推广为**比较轴**：从答案属性（第 4.2 节）中选一个作为对比的列，其余属性要么固定为某个取值，要么显式声明为"不限"。

```text
python -m scoring compare --axis profile [--fix mode=natural] [--any trial] [--questions <筛选条件>]
```

- 输出题目 × 比较轴的通过矩阵，以及各维度在每个轴值上的通过率与区间。轴值数量不限，不再只支持两个 run。
- 放行条件：除比较轴外，没有被固定或声明为"不限"的属性必须在所有答案上取值一致，否则拒绝并列出不一致的属性。`skills_mode` 不同时始终拒绝。
- 所有答案按同一份当前期望、同一链配置下的有效结论比较。缺少判定的答案提示"待重判"，不参与比较。原来的算子版本护栏随之不再需要。

### 7.2 按题目交集对齐

比较只在双方（或各方）**共有的 `qkey`** 上进行：

- 降级移出或退役的题，在某一方不存在，自然被排除；
- 输入改过的题 `qkey` 不同，自然被排除；
- 只改了期望的题经重判后，按同一份期望比较。

这样比 diff.md 的"因降级移出"对齐更严格，04 §7 的分母对齐改为按题目交集实现。diff.md 仍可以传入，用于在报告中列出被排除的题及原因。

锚点绊线（上一 run 全部 trial 通过、本 run 全部失败，trials ≥ 2）沿用现行逻辑，改为按 `qkey` 匹配。

## 8. 复核服务（C13）

所有视图从评测库取数并分页，删除 `RunStore` 和 `Index`，不再在请求中加载 jsonl 或全量重算。

| 视图 | 内容 |
| --- | --- |
| 题目列表（首页） | 按维度、主题、标签、活跃状态筛选；按难度、区分度、稳定性、待复核数排序；顶部为维度 × 比较轴的通过率矩阵 |
| 题目视图 | 当前期望固定在上方；答案按所选比较轴分列，轮次为行；每轮下方显示条目的有效结论与来源；只列同一 `qkey` 的答案；可切换查看历史期望下的结论 |
| 题组视图 | 种子与变体为行，比较轴为列，展示题组一致性；诱导变体单独标注 |
| 复核队列 | 未决、会话失败、人工与机器不一致、待重判的条目，分页，快捷键操作 |
| 比较 | 第 7 节的比较轴与题目矩阵 |
| 质量 | 04 §7 第 3 类出口，含 C5 的变体泄露嫌疑清单、作废的人工改判 |

- 总览中有被排除的未决答案时，通过率旁标注"临时（已排除未决 N 条）"，沿用 08 v2 的规则。
- 改判提交在一个事务内完成：校验、写入 reviews、重算该答案的结论行。
- 服务不触发算子：重判通过命令行完成，页面只显示待重判数。
- 默认只监听本机，沿用 08 v2。

## 9. 存储层隔离与演进（C15）

- `scoring/store.py` 是唯一访问评测库的模块，提供面向业务的接口（入库答案、写入判定、追加改判、查询题目与答案、聚合统计等）。其他模块不直接拼 SQL。
- 只用标准 SQL，少用 SQLite 特有语法（`INTEGER PRIMARY KEY` 自增除外，迁移时替换为对应写法）。
- `meta.schema_version` 记录库版本，启动时按版本顺序执行迁移脚本。

后续按触发条件演进，不切换到 k-v 存储：

| 触发条件 | 动作 |
| --- | --- |
| 分析查询变慢 | 引入 DuckDB，只读挂载 SQLite 文件或读取导出的 Parquet；SQLite 仍负责写入 |
| 需要多人同时在线复核 | 评测库迁移到 PostgreSQL，只改存储层 |
| 数据量超出单机 | 考虑 ClickHouse 等分布式分析库（按当前估算不太可能发生） |

## 10. 命令行（C14）

| 命令 | 作用 | 是否调用算子 |
| --- | --- | --- |
| `ingest <run>` | 登记 run、题目、执行时所用期望、答案；可重复执行 | 否 |
| `specs import <dist.jsonl>` | 导入评测集期望，更新当前期望 | 否 |
| `specs set-current <evalset_version>` | 指定某个版本的期望为当前期望 | 否 |
| `score <run>` | 等价于 `ingest` 加上对该 run 的答案按当前期望判定 | 是 |
| `rejudge [--question] [--run]` | 补判缺少"当前期望 + 当前链配置"判定的答案 | 是 |
| `rescore [--policy]` | 只重算会话结论表 | 否 |
| `compare --axis …` | 第 7 节的比较 | 否 |
| `export [--run] [--spec at-run\|current]` | 导出 verdicts、reviews、scoring.json、CSV；`--spec at-run` 按执行时的期望导出该 run 当时的报告 | 否 |
| `backup <目标文件>` | 用 SQLite 原生备份接口复制评测库 | 否 |
| `import-legacy <run>` | 一次性导入现有 `verdicts.jsonl`、`review.jsonl`、`verdict-cache.jsonl` | 否 |
| `serve` | 复核服务 | 否 |

命令行路径（除 serve 外）仍然只依赖标准库和 PyYAML，CI 不受服务依赖影响。
